# 项目迁移：Agentic 智能体驱动检索决策（第三版）

> 本文档是**第三版（Agentic 版）的完整实施与迁移文档**，目标是基于现有 `product/backend` 迁移出一套
> 「由 LLM 全程驱动的检索决策」系统。内容覆盖：架构设计、目录规划、后端实现、工具封装、API、前端、
> 配置、部署、评估与提示词，全链路可落地。
>
> **迁移三注意**（全文贯彻，务必在实现时显式遵守）：
> 1. **单问题 Agent 最多重复决策 3 次**——第 3 轮必须收敛，禁止继续发起工具调用（见 §4、§9）。
> 2. **评估模块要具体**——给出测试集、指标公式与裁判提示词，可复跑、可答辩（见 §10）。
> 3. **尽量复用现有代码**——检索、生成、引用、裁判全部复用 `product/backend` 与 `demo`，新增代码仅限「调度层」（见 §2、§5）。

---

## 1. 迁移目标与三版关系

| 形态 | 目录 | 定位 | 检索决策由谁做 |
| --- | --- | --- | --- |
| 验证版 | `demo/` | 验证混合检索 + Rerank 链路 | 写死的固定管道 |
| 产品级 | `product/` | 链路产品化（多知识库/多轮/日志/深色） | 知识库固定策略配置 |
| **Agentic（本次新增）** | `agent/` | LLM 全程驱动检索决策 | **LLM 逐轮决策** |

**核心变化一句话**：前两版是无条件跑完 `召回→融合→精排→生成` 的确定管道；第三版把 LLM 前置为调度大脑，
由它逐轮决策「是否检索、用什么策略、结果够不够、要不要改写重查、还是干脆闲聊」。

**迁移原则**：**复用 > 重写**。检索链路、生成、引用、入库、存储、多轮历史全部复用现有模块，
`agent/` 只新增一层**调度编排**，不复制不改造底层检索/生成逻辑。

## 2. 整体架构设计

Agentic 版在 `product/backend` 之上叠加三层：

```
┌─────────────────────────────────────────────────────────┐
│ ① Agent 调度层（本次新增）                                │
│   loop.py（ReAct 循环）· state.py（状态）· prompts.py     │
│   ── LLM 逐轮决策：闲聊直接答 / 澄清 / 检索 / 直接回答 ── │
├─────────────────────────────────────────────────────────┤
│ ② 工具层（薄封装，本次新增）                              │
│   tools.py：retrieve / ask_clarification                 │
│   ── 每个工具只是「参数校验 + 调复用层函数 + 回填轨迹」──  │
├─────────────────────────────────────────────────────────┤
│ ③ 复用层（现有 product/backend，零改动）                  │
│   retrieval_service · contexts_from_results · LLMClient  │
│   citation · db models · storage · ingest · kb_service   │
└─────────────────────────────────────────────────────────┘
```

### 数据流（一次 Agent 问答）

```
用户问题
  ↓
AgentLoop.run(question, kb_id, history)
  ├─ 第 1 轮：LLM 决策（意图路由 + 改写 query + 选 strategy）
  │     ├─ 闲聊               → LLM 直接输出闲聊回复，结束
  │     ├─ ask_clarification  → 反抛问题给用户，暂停
  │     └─ retrieve(query,strategy) → 调 retrieval_service，进第 2 轮
  ├─ 第 2 轮：LLM 评估证据，不足则改写重查 / 足够则直接输出答案
  └─ 第 3 轮：强制输出最终答案（无论证据是否充分）
  ↓
LLM「不调工具、直接输出 content」即为最终答案（含 [n] 引用）
  → 复用 citation.extract_citations 解出引用（映射逻辑零改动）
  ↓
返回 {answer, citations, retrieved_docs, trace, latency}
```

### 关键设计决策：最终答案怎么生成

| 方案 | 做法 | 取舍 | 结论 |
| --- | --- | --- | --- |
| **方案 A（采用）** | Agent 直接产出最终答案（含 `[n]` 引用），不经过二次生成 | 省一次调用、降延迟；需在 `AGENT_SYSTEM` 声明引用规则并保证编号一致 | ✅ 采用 |
| 方案 B（备选） | Agent 只收集证据，最终答案交给 `PromptBuilder` + `LLMClient.generate` 生成 | 引用格式与 `citation` 零风险兼容，但多一次 LLM 调用 | 不采用 |

## 4. 后端实现方案

### 4.1 `loop.py` —— Agent 循环（核心新增）

```python
"""调度循环：最多 3 轮决策，每轮 LLM 要么调工具，要么直接输出最终答案（content）。"""
from __future__ import annotations
from dataclasses import dataclass, field
from src.core.config import settings
from src.generation.llm import get_llm_client
from src.agent.state import AgentState
from src.agent.tools import execute_retrieve
from src.agent.prompts import AGENT_SYSTEM, TOOL_SCHEMAS, FORCE_ANSWER_INSTRUCTION

MAX_DECISION_ROUNDS = settings.agent.max_decision_rounds   # 默认 3，← 硬约束：单问题最多 3 轮决策
MAX_RETRIEVE_CALLS = settings.agent.max_retrieve_calls     # 检索工具最多调用次数（默认 3）

@dataclass
class AgentResult:
    answer: str = ""
    citations: list = field(default_factory=list)
    retrieved_docs: list = field(default_factory=list)
    trace: list = field(default_factory=list)     # 决策轨迹（每轮一条）
    rounds: int = 0
    latency: dict = field(default_factory=dict)
    is_clarification: bool = False
    clarification_question: str | None = None


class AgentLoop:
    def __init__(self, llm_client=None):  # llm_client 复用 get_llm_client()
        self.llm = llm_client or get_llm_client()
        self.max_rounds = MAX_DECISION_ROUNDS
        self.max_retrieve_calls = MAX_RETRIEVE_CALLS

    def run(self, question: str, kb_id: int, history: list) -> AgentResult:
        state = AgentState(question=question, kb_id=kb_id, history=history)
        state.build_initial()
        retrieve_calls = 0

        for round_no in range(1, self.max_rounds + 1):
            decision = self._decide(state)          # 一次 Function Calling 调用

            # 不调工具 = LLM 直接输出最终答案（含 [n] 引用）→ 结束
            if not decision.tool_calls:
                return self._finish(state, decision.content)

            call = decision.tool_calls[0]
            name, args = call["name"], self._parse_args(call["arguments"])
            if name == "ask_clarification":
                return self._clarify(state, args["question"])   # 暂停循环，等用户补充
            if name != "retrieve" or retrieve_calls >= self.max_retrieve_calls:
                return self._force_finish(state)                # 未知工具 / 次数用尽 → 强制收敛

            execute_retrieve(state, args["query"], args["strategy"])  # 检索并回填证据
            retrieve_calls += 1

        # 兜底：触顶 3 轮仍只调工具 → 追加「必须作答」指令，强制让 LLM 输出答案
        return self._force_finish(state)
```

**三条保底**（对应"最多 3 次决策"）：
- `MAX_DECISION_ROUNDS = 3`，`for` 循环天然封顶；
- LLM 不调工具、直接输出内容即为最终答案，立刻退出；
- 触顶后追加「必须作答」指令强制 LLM 输出，绝不无限循环。

### 4.2 `state.py` —— Agent 状态

```python
@dataclass
class AgentState:
    question: str
    kb_id: int
    history: list            # [(role, content), ...]，复用 chat_service._recent_history 产出
    messages: list = field(default_factory=list)   # 喂给 LLM 的决策上下文（含工具结果）
    evidences: list = field(default_factory=list)  # 累积的 RetrievalResult（跨轮去重）
    _seen: set = field(default_factory=set)        # 已收录 chunk_id，用于去重
    trace: list = field(default_factory=list)      # 每轮 {round, action, tool, args, ...}
    rounds: int = 0

    def build_initial(self) -> None:
        """system(AGENT_SYSTEM) + 最近 N 轮历史 + 当前问题。"""

    def add_evidences(self, results: list) -> list:
        """按 chunk_id 去重后追加，返回本轮新增子序列。"""

    def evidence_contexts(self) -> list:
        """contexts_from_results(self.evidences, start_index=1)，编号跨轮连续。"""

    def append_turn(self, assistant_msg: dict, tool_msg: dict) -> None:
        """把 assistant(tool_calls) 与 tool(result) 两则消息追加进 messages。"""
```

### 4.3 `tools.py` / `prompts.py` —— 工具层（薄封装，复用检索）

> 工具 JSON Schema 放在 `prompts.py` 的 `TOOL_SCHEMAS`（与最终生成用的 `settings.generation.system_prompt` 互不冲突）。

```python
"""每个工具 = 参数校验 + 调复用层 + 回填轨迹。不含任何检索/生成业务。"""

def execute_retrieve(state: AgentState, query: str, strategy: str) -> dict:
    from src.services.retrieval_service import retrieve   # ← 复用，零改动
    resp = retrieve(state.kb_id, query, strategy_to_switches(strategy))
    new = state.add_evidences(resp.results)               # 累积证据（按 chunk_id 去重）
    start_index = len(state.evidences) - len(new) + 1      # 跨轮编号连续
    rendered = "\n\n".join(c.render() for c in contexts_from_results(new, start_index))
    state.trace.append({...})
    return {"query": query, "strategy": resp.strategy, "result_count": len(resp.results),
            "new_count": len(new), "rendered": rendered, "docs": [...],
            "stats": resp.stats, "elapsed_ms": ...}
```

`strategy_to_switches` 是唯一的映射函数（策略名 → 现有四开关）：

```python
_SWITCHES = {
    "vector":        {"vector": True,  "bm25": False, "fusion": False, "rerank": False},
    "bm25":          {"vector": False, "bm25": True,  "fusion": False, "rerank": False},
    "hybrid":        {"vector": True,  "bm25": True,  "fusion": True,  "rerank": False},
    "hybrid_rerank": {"vector": True,  "bm25": True,  "fusion": True,  "rerank": True},
}
```

### 4.4 `agent_service.py` —— Agent 门面

会话与消息的写入/读取沿用 product 的 `chat_service`（本版已删除其固定管道问答函数，只保留会话 CRUD、
`_recent_history`、`_save_message`、`sse`）。Agent 门面在此之上组合：

- `prepare_agent_stream()`：建会话、存用户消息、取历史，并在线程池执行 `AgentLoop.run` 得到完整结果后组装 SSE；
- SSE 事件流在现有 `meta / delta / done` 之外**增加** `agent_step` 事件（每轮决策/工具结果实时推给前端时间线）；
- 最终答案由 Agent 直接输出（方案 A 单次产出，`delta` 一次推送全文，不逐 token 流式），
  引用解析复用 `citation.extract_citations`（传入累积证据）。

### 4.5 决策轨迹落库

不新增表，复用现有 `Message.latency` JSON 列（与现有 `strategy`/`stats` 同法），把精简轨迹塞进 `latency["agent_trace"]`；
详细轨迹通过 SSE 实时返回前端，仅在需要审计时持久化。这样迁移成本最小。

## 6. API 路由设计

复用现有 [chat.py](file:///c:/Users/98429/Documents/DeskDock/library/基于混合检索与Rerank的领域知识库系统/product/backend/src/api/v1/chat.py) 的路由结构，新增 `/agent` 前缀，挂在 `src/api/v1/__init__.py` 的 `api_router` 上：

```
POST /api/v1/agent/chat          # Agent 问答（非流式）
POST /api/v1/agent/chat/stream   # Agent 问答（流式 SSE，含 agent_step 事件）
GET  /api/v1/conversations       # 会话列表（沿用 product 会话管理）
```

原固定管道接口 `POST /api/v1/chat`、`POST /api/v1/chat/stream` **已下线**，`chat.py` 只保留会话管理；
可选审计端点 `GET /agent/trace/{conversation_id}` 未实现（轨迹已内嵌 `latency.agent_trace`，前端按需还原）。

请求体沿用原 `/chat` 的字段语义（`kb_id / question / conversation_id / image`），**去掉** `strategy` 字段
（策略由 Agent 决定，不再由前端/知识库固定传入）——这是与固定管道问答的语义差异。

响应体在固定管道问答的响应字段基础上新增：

```json

  "answer": "...", "citations": [...], "retrieved_docs": [...],
```

## 9. 提示词（三份 + 三工具 Schema）

> 全部集中在 `src/agent/prompts.py`。这是 Agentic 版**新增**的提示词，与现有
> `settings.generation.system_prompt`（第七节最终生成用）互不冲突。

### 9.1 `AGENT_SYSTEM` —— 决策大脑

```python
AGENT_SYSTEM = """你是一个领域知识库问答系统的智能调度器（Agent）。你可以调用工具检索知识库，也可以直接给出最终回答。

你的唯一目标：在最多 3 轮决策内，给出准确、可溯源的最终回答。

【每一轮只能做一件事：调用一个工具（retrieve / ask_clarification），或直接输出最终回答（不调用任何工具）。】

—— 第 1 轮：意图识别 + 首次检索 ——
1. 闲聊/寒暄/自我介绍（如「你好」「谢谢」「在吗」「你是谁」）：
   直接输出友好自然的回答，不要调用任何检索工具。
2. 问题存在关键歧义（指代不明、多个可能对象、缺少必要背景）：
   调用 ask_clarification 反问用户，不要猜。
3. 需要知识库依据才能回答的问题：
   先把用户口语改写成规范领域检索 query（去口语、补全指代、用规范术语），
   再调用 retrieve(query=改写后, strategy=最合适的策略)。

—— 第 2 轮：结果评估 + 补充检索 / 直接作答 ——
1. 证据已足够 → 直接输出最终回答，并在需要依据处用 [编号] 标注来源。
2. 证据不足 → 改写 query（换关键词/换角度）再调用 retrieve，禁止提交完全相同 query。

—— 第 3 轮：强制收敛 ——
无论证据是否充分，都必须直接输出最终回答，禁止再调用任何工具。

【回答与引用的硬性规则】
1. 只能依据【已检索到的证据】回答，不得使用证据之外的知识，不得臆测或编造。
2. 证据与问题无关或不足以支撑时，直接回答「根据现有资料无法回答该问题」，并说明缺少哪些信息。
3. 直接输出最终回答时，用 [编号] 标注每条结论的依据来源（编号必须严格对上证据列表里的 [编号]），例如：应在规定期限内提出申请[1]。
4. 回答使用中文，结构清晰；涉及步骤或对比时优先分点或表格；多条规定不一致时如实指出冲突并分别列明。

【硬性约束】
1. 单问题最多 3 轮决策；第 3 轮必须直接输出最终回答。
2. 闲聊禁止调用检索工具。
3. 检索查询使用中文规范术语。"""
```

### 9.3 最终答案生成（方案 A：Agent 直接产出）

采用**方案 A**：Agent 不调工具、直接输出的 content 即为最终答案，**不经过第二次 `PromptBuilder` 生成**。
省掉一次 LLM 调用、降低延迟；代价是引用规则需自行保证，约定如下：

- **引用规则**：已并入 `AGENT_SYSTEM`（§9.1「回答与引用的硬性规则」），不再依赖 `PromptBuilder.build_system_prompt()` 自动追加。原有的 5 条严谨规则（仅依据资料、不足说明、中文结构、归纳整合、冲突列明）已折进 `AGENT_SYSTEM`。
- **证据编号**：`state.to_messages()` 用现有 `contexts_from_results` / `PromptContext.render` 把累积证据渲染成 `[1] 来源：xxx 页码：xxx` 格式（与验证版一致的编号体系），保证 LLM 引用的 `[n]` 能回映射到实际文档块。
- **引用解析**：复用 `citation.extract_citations(answer, 累积证据)`，映射逻辑零改动。
- **闲聊**：与知识问答统一为「LLM 直接输出 content」，仅闲聊首轮即答、不进检索。

## 10. 评估模块（具体）

复用 `demo/src/evaluation/` 骨架与 [judge.py](file:///c:/Users/98429/Documents/DeskDock/library/基于混合检索与Rerank的领域知识库系统/demo/src/evaluation/judge.py) 的 `LLMJudge`，
在其上新增 agentic 特有指标。两类：**程序化统计**（不耗 token）与 **LLM 裁判**（耗 token）。

### 10.1 测试集构成（建议共 80 条）

| 意图标签 | 含义 | 数量 | 来源 |
| --- | --- | --- | --- |
| `chitchat` | 闲聊/寒暄 | 20 | 新增 |
| `knowledge` | 单跳知识问答 | 25 | 沿用现有测试集 |
| `multi_hop` | 多跳/复合（需多步检索或对比） | 20 | 新增 |
| `ambiguous` | 有歧义需澄清 | 15 | 新增 |

每条标注 `ground_truth_intent` 与 `gold_chunks`（正确答案所在块）。

### 10.2 程序化指标（零 token）

```
总体路由准确率    = 正确路由条数 / 总条数
chitchat 正确拦截率 = 正确判为闲聊 / chitchat 总数         （应→1.0，这是核心痛点）
knowledge 正确检索率 = 正确判为需检索 / knowledge 总数      （应→1.0）
工具调用成功率      = 合法且返回成功 / 总调用次数
平均决策轮数        = Σ决策轮数 / 样本数                   （应 ≤3，越接近 1 越高效）
3 轮触顶率         = 用满 3 轮样本数 / 样本数              （越低越好）
重复检索率         = 出现完全相同 query 重复检索样本占比    （应→0，检验防死循环）
```

判定方式：解析 Agent 执行轨迹 `trace` 与 `ground_truth_intent` 对比，不调 LLM。

### 10.3 沿用裁判（不改）

`faithfulness`（忠实度）、`answer_relevancy`（答案相关性），量程 1~5，直接复用
`LLMJudge` + `_JUDGE_SYSTEM` + `_JUDGE_USER`，新增样本同样交给它打分，保证与验证版指标可比。

### 10.4 新增裁判：任务完成率 `task_completion`（量程 1~5）

```python
_TASK_COMPLETION_JUDGE_SYSTEM = """你是一位严格、公正的任务完成度评审员。判断"代理（Agent）给出的答案是否完整回答了用户的多跳/复合问题"。

评分要求：
1. 只依据【用户问题拆解出的子问题要点】与【用户问题】判断，不引入你自己的知识。
2. 先给理由再给分数，理由要指出具体遗漏了哪个子问题。
3. 只输出 JSON，不要输出其它文字或代码块标记。

评分标准（1~5 整数）：
- task_completion：是否回答了所有子问题/所有诉求。
  5 = 所有子问题都准确回答，无遗漏，关联处解释清楚；
  4 = 主要子问题都回答，个别次要诉求略有遗漏；
  3 = 回答了部分子问题，但有一个关键子问题被遗漏或敷衍；
  2 = 只答单一层面，大部分子问题未触及；
  1 = 基本未回答，或完全答非所问。
注意：若答案诚实说明"部分无法回答（资料不足）"，且核对资料确实不足，该子问题视为正确处理，不扣分。"""

_TASK_COMPLETION_JUDGE_USER = """【用户问题】
{question}

【用户问题拆解出的子问题要点】
{sub_questions}

【候选答案】
{answer}

请严格按以下 JSON 输出（分数必须是 1~5 整数）：
{
  "task_completion": {"score": <1-5>, "reason": "<简要理由，50 字内>"}
}"""
```

### 10.5 指标汇总与对比口径

| 指标 | 类型 | 量程 | 方向 |
| --- | --- | --- | --- |
| 路由准确率 / chitchat 正确拦截率 | 程序化 | 0~1 | 越高越好 |
| 工具调用成功率 | 程序化 | 0~1 | 越高越好 |
| 平均决策轮数 / 3 轮触顶率 / 重复检索率 | 程序化 | 见上 | 越低越好 |
| faithfulness / answer_relevancy | LLM 裁判 | 1~5 | 越高越好（沿用） |
| task_completion | LLM 裁判 | 1~5 | 越高越好（新增） |

> 检索类指标（Recall/MRR/nDCG）仍沿用验证版口径，说明"链路没被 Agent 拖垮"；
> 路由 / 工具 / 完成率三类说明"Agent 调度是否有增益"。两组共同回答「Agentic 是否真的更好」。
