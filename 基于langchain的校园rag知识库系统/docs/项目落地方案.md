# 校园内部 RAG 知识库项目落地方案

> 依据现有仓库能力评估编写，目标是把「基于混合检索与 Rerank 的领域知识库系统」从技术验证形态改造为可在学校内部真实运行的问答系统。
>
> 编写日期：2026-11-10

---

## 一、项目现状评估

### 1.1 三种形态对比

仓库内为同一检索链路的三种实现，索引、数据、配置相互独立。

| 形态 | 目录 | 定位 | 技术栈 | 端口（后端/前端） | 数据库 |
| --- | --- | --- | --- | --- | --- |
| Demo 验证版 | `demo/` | 验证核心链路，附带完整评估体系 | Streamlit + FastAPI | 8001 / 5171 | 本地 |
| Product 产品级 | `product/` | 多知识库、文档入库、多轮对话、日志、深色模式 | Vue 3 + Element Plus + FastAPI | 8002 / 5172 | `rag_product` |
| Agentic 智能体版 | `agent/` | LLM 逐轮决策检索，最多 3 轮收敛，多模型热切换 | React 18 + Vite + FastAPI | 8003 / 5173 | `rag_agent` |

共同检索链路（三版完全一致）：

```
向量 Top-50  ‖  BM25 Top-50
      ↓
RRF 融合（k = 60）→ 候选池 20 条
      ↓
bge-reranker-v2-m3 精排 → Top-5
      ↓
上下文拼接（预算 6000 字）→ LLM 生成带引用答案
```

### 1.2 与学校场景的匹配度

优势集中在三点：

1. **文档形态同构。** 现有语料为法律领域（章-节-条、交叉引用、文号、生效日期），与《学生手册》《教务管理规定》《奖助学金评定办法》结构高度一致，更换语料基本不需要改动检索链路。
2. **强制引用可溯源。** 三版均强制 `[n]` 引用标注并回映射到「文件名 + 页码」，符合学校问答场景对「答错代价高」的约束。
3. **混合检索的动机真实成立。** 学生口语化提问与制度文本措辞不一致，需要向量召回；「第三十八条」「校教〔2023〕7 号」这类精确串需要 BM25 命中，两者互补。

### 1.3 差距清单

按「不补就上不了线 / 上线会出事 / 影响体验」分级。

| 级别 | 差距 | 现状证据 | 改造方向 |
| --- | --- | --- | --- |
| P0 | 零鉴权、零用户体系 | 三个后端 `db/models` 仅含 conversation / document / knowledge_base / message / retrieval_log，全仓无 auth / user / role 相关代码 | 接入学校统一身份认证（CAS / 企业微信 / 钉钉 OAuth）；新增 user 表与 RBAC；文档级 ACL |
| P0 | 无权限过滤 | 检索链路不含任何 filter 条件 | 在检索层按用户角色与文档密级过滤，禁止事后过滤 |
| P0 | 无文档生命周期 | 入库为一次性全量重建 | 文档版本、生效日期、废止下线、增量重建 |
| P1 | 表格解析弱 | 解析器仅 pdf / docx / text，分块为通用切分，无表格与父子块处理 | 表格转 Markdown 或结构化抽取；条款级结构化分块 |
| P1 | 无移动端 | 三版均为 PC Web 布局 | 响应式 H5，或提供企业微信 / 钉钉入口 |
| P1 | 性能与成本未压测 | 精排单模型、无并发与缓存设计 | GPU 推理、批量精排、热点问题缓存 |
| P2 | 运维组件偏重 | MySQL + MinIO + Redis + Celery + Chroma | 收敛为单机 docker-compose，MinIO 换本地盘，Celery 可退化为同步任务 |
| P2 | 部署配置硬编码 | `core/config.py` 中 `resource_dir` 指向个人桌面路径 | 改为相对路径或环境变量 |
| P2 | 无反馈闭环 | 无点赞 / 纠错入口 | 增加答案反馈与错题上报 |

## 二、落地目标与范围

### 2.1 目标

1. 学生与教职工通过统一身份登录，看到的答案与其身份权限一致。
2. 制度类问题答案必须给出可点击的依据（文件名 + 条款 + 页码）。
3. 旧版制度下线后不再被召回，不出现新旧条款冲突作答。
4. 首期覆盖教务处一个部门的知识库，问题覆盖率达到该部门高频咨询问题的 70% 以上。

### 2.2 首期不做的事

- 不做全部门一次性上线，避免知识库治理跟不上。
- 不做全 Agent 架构，避免简单问题的延迟与成本翻倍。
- 不做跨系统数据打通（学籍、成绩、一卡通），避免引入个人信息合规风险。

## 三、总体方案

### 3.1 底座选型

**以 LangChain 作为检索与生成链路的统一框架，从零构建独立后端；`demo/`、`product/`、`agent/` 只作为行为参考，不作为运行依赖。**

理由：

- 校园问答的核心是稳定的「加载、切分、索引、混合召回、精排、受约束生成」管道，LangChain 把这些环节抽象为可替换组件，后续换嵌入模型、换向量库、加文档 ACL 时不需要重写业务流程。
- 混合检索用 `EnsembleRetriever`（RRF）组合向量召回与 `BM25Retriever`，精排用 `ContextualCompressionRetriever` 叠加 `CrossEncoderReranker`，参数集中可配，便于评估回归。
- 生成侧用 LCEL 组合 Prompt、聊天模型与输出解析，流式输出、引用编号、拒答规则都能在同一链路中实现。
- 三版历史实现的检索参数（向量 Top-50、BM25 Top-50、RRF k=60、精排 Top-5）作为初始默认值保留，但不复制其代码。

### 3.1.1 技术栈

| 层次 | 组件 |
| --- | --- |
| Web 框架 | FastAPI + Uvicorn |
| 数据访问 | SQLAlchemy 2 异步 ORM + Alembic 迁移 + MySQL 8 |
| 认证 | 本地账号密码 + bcrypt + JWT（服务端可撤销会话表） |
| 检索框架 | LangChain（`langchain`、`langchain-community`、`langchain-chroma`、`langchain-huggingface`） |
| 文档加载 | `PyPDFLoader`、`Docx2txtLoader`、`TextLoader` |
| 分块 | `RecursiveCharacterTextSplitter`（中文分隔符定制） |
| 向量库 | `Chroma`（本地持久化，按知识库分集合） |
| 关键词检索 | `BM25Retriever` + `rank_bm25` |
| 融合与精排 | `EnsembleRetriever`（RRF）+ `CrossEncoderReranker` |
| 生成 | LCEL 链 + `ChatOpenAI`（兼容 DeepSeek 等 OpenAI 协议服务） |
| 缓存与限流 | Redis（会话限流、登录失败计数） |
| 前端 | Vue 3 + Vite + Element Plus + Pinia + Vue Router |

### 3.2 目标架构

```
接入层   统一身份认证（本地账号，预留 CAS / 企业微信适配器）→ 会话与角色解析
           ↓
应用层   问答 / 知识库管理 / 检索策略 / 日志审计 / 反馈
           ↓
检索层   权限过滤 → Chroma 向量召回 ‖ BM25 召回 → EnsembleRetriever 融合
          → CrossEncoderReranker 精排 → 上下文拼接（Document 列表）
           ↓
生成层   LCEL 链（ChatPromptTemplate + ChatOpenAI + 输出解析与引用编号）
           ↓
存储层   MySQL（业务数据） + 本地磁盘（文档） + Chroma 索引 + BM25 索引文件
```

要点：

- 检索与生成全部通过 LangChain 的 `Document`、`Retriever`、`Runnable` 抽象串联，业务层只负责归属校验、策略解析与日志记录。
- 权限过滤前置到检索层：知识库可见性在构造 retriever 之前解析，过滤条件写入 Chroma 的 `filter`，BM25 侧按文档元数据裁剪，避免融合阶段把无权限文档带进候选池。
- 双通道生成：默认走云端 OpenAI 协议服务；涉及学生个人信息的材料后续强制走本地模型，数据不出校。
- 检索日志与系统日志记录用户、角色、策略、命中文档 ID，供管理端排障与后续评估回归使用。

### 3.3 权限模型

三级角色，叠加文档密级：

| 角色 | 可见范围 | 典型用户 |
| --- | --- | --- |
| student | 密级为「公开」的文档 | 在校学生 |
| staff | 公开 + 本部门内部文档 | 辅导员、院系教务员 |
| admin | 全部文档，含配置与日志 | 信息中心、教务处管理员 |

实现要求：

1. 文档入库时必须指定密级与归属部门，缺省不开放。
2. 检索请求携带角色与部门，在向量检索与 BM25 检索的过滤条件中同时生效，避免融合阶段把无权限文档带进候选池。
3. 无权限文档即使命中也不出现在引用列表中，避免通过引用反推内容。

### 3.4 文档生命周期

新增字段：文档版本号、生效日期、废止日期、责任部门、责任人、状态（草稿 / 已发布 / 已废止）。

规则：

1. 同一制度的新版本发布时，旧版本自动置为已废止，并从索引中移除。
2. 答案页展示依据时，明确标注版本与生效日期，例如「依据：《XX 管理办法》（2025 修订）第三十八条」。
3. 支持单文档增量重建，不触发全量索引重建。
4. 文档入库后进入「草稿」状态，经责任人确认后才进入检索范围。

### 3.5 部署形态

学校信息中心的实际维护能力决定部署必须收敛：

- 单机 docker-compose：后端服务 + MySQL + 本地存储目录 + 可选 Ollama。
- 去掉 MinIO，文档落本地磁盘并按知识库分目录。
- Celery 首期可退化为同步任务，文档量上来后再引入队列。
- 提供一键启动与健康检查脚本，沿用现有 `start_all.py` 的思路改造。
- 上线前清除硬编码路径，全部配置走环境变量。

## 四、分阶段实施计划

### 第一阶段：能看能问

交付内容：

1. 统一身份认证接入，用户表与 RBAC 落地。
2. 文档级 ACL，检索层权限过滤生效。
3. 知识库管理页复用 product 现有页面结构，增加密级与责任部门字段。
4. 引用溯源在答案页可点击，落到「文件 + 页码」。
5. 仅接入教务处一个部门的知识库。

验收标准：

- 学生账号检索不到内部文档，且答案中不出现相关引用。
- 任意一条答案的依据均可回溯到原文页面。
- 单问端到端响应时间在可接受范围内，精排环节完成 GPU 化或批量化。

### 第二阶段：能信

交付内容：

1. 文档版本、生效日期、废止下线、增量重建。
2. 答案页固定展示依据文件的版本与生效日期。
3. 答案纠错与点赞反馈入口，反馈进入后台待办。
4. 基于真实咨询工单构建 300~500 条黄金测试集，接入 demo 的评估模块做回归。
5. 人工转接通道：答不了的问题可转对应科室。

验收标准：

- 新旧版本制度同时存在时，只召回有效版本。
- 黄金测试集上的检索命中率与答案正确率有基线记录，每次改动可对比。
- 每条回答带免责声明，且可追溯到责任部门。

### 第三阶段：好用

交付内容：

1. 移动端 H5 或企业微信 / 钉钉入口。
2. 热点问题缓存，降低高频重复提问的成本与延迟。
3. 深度问答开关，接入 Agent 决策循环。
4. 按部门拆分知识库，支持多部门并行治理。

验收标准：

- 移动端可完成完整问答与引用查看流程。
- 热点问题命中缓存后响应明显加快。
- 深度问答触发时有明确的决策轨迹展示，且轮数不超过 3 轮。

## 五、关键改造点清单

| 改造点 | 涉及模块 | 说明 |
| --- | --- | --- |
| 身份与角色 | `backend/src/db/models.py`、`backend/src/api/deps.py`、`backend/src/services/auth_service.py` | 用户、角色、会话表与依赖注入，后端逐请求校验角色与状态 |
| 检索层权限过滤 | `backend/src/retrieval/retrievers.py` | 知识库可见性在构造 retriever 前解析，过滤条件下推到向量与 BM25 两路 |
| 文档生命周期 | `backend/src/db/models.py`、`backend/src/services/knowledge_service.py`、`backend/src/ingest/pipeline.py` | 文档状态、单文档重建、废止文档从索引移除 |
| 结构化分块 | `backend/src/ingest/loaders.py`、`backend/src/ingest/splitter.py` | 使用 LangChain 加载器与中文分隔符切分，条款级切分在阶段二增强 |
| 双通道生成 | `backend/src/generation/llm.py`、`backend/src/generation/chain.py` | 按配置选择模型服务，链路由 LCEL 组合 |
| 引用编号 | `backend/src/generation/chain.py`、`backend/src/services/chat_service.py` | 检索结果转 `[n]` 引用并回写消息元数据 |
| 反馈闭环 | `backend/src/services/feedback_service.py`、`frontend/src/views/FeedbackAdmin.vue` | 快照由后端生成，状态流转可追踪 |
| 部署配置 | `backend/src/core/config.py`、`.env.example`、`docker-compose.yml` | 全部路径相对项目根推导，端口与库名独立 |

注意：`demo/` 的评估模块（`demo/src/evaluation/`）是现有资产中最具复用价值的部分，校园版测试集应直接复用其指标定义与裁判逻辑，避免重新实现。

## 六、评估与验收指标

| 维度 | 指标 | 说明 |
| --- | --- | --- |
| 检索质量 | Recall@k、MRR | 基于黄金测试集，按知识库分别统计 |

## 七、风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 答案错误引发行政纠纷 | 学生持截图质疑教务处 | 答案页强制免责声明 + 依据版本标注 + 人工转接通道 |
| 知识库无人维护 | 文档过期后系统持续给错误答案 | 每个知识库指定责任部门与责任人，文档带有效期，到期提醒复核 |
| 个人信息外泄 | 合规风险 | 涉密材料强制本地模型，日志脱敏并设保留期限 |
| 性能不达标 | 高峰期不可用 | 精排 GPU 化、批量推理、热点缓存、限流降级 |
| 运维能力不足 | 服务长期不可用 | 单机 docker-compose，减少中间件，提供健康检查与备份脚本 |
| Agent 路径延迟过高 | 体验下降 | 仅对多跳问题启用，保持 3 轮上限，可随时关闭 |

## 八、待决策事项

1. 身份认证方式：CAS、企业微信还是钉钉，取决于学校现有基础设施。
2. 首期知识库范围：建议教务处，需确认该部门是否愿意指派维护责任人。
3. 生成模型策略：公开制度是否允许走云端 API，需信息中心与合规部门确认。
4. 部署位置：校内机房自建 GPU，还是使用校内已有算力平台。
5. 移动端形态：独立 H5 还是直接嵌入企业微信工作台。
