## 一、阶段目标

一句话概括：

> 在不绕过权限、版本与引用规则的前提下，让系统从「教务处可用」扩展到「多部门可治理」、从「电脑可用」扩展到「手机可用」、从「固定管道」扩展到「复杂问题可深度分析」，并让热点问题更快、运营有数据。

本阶段必须达成以下结果：

1. **多部门并行治理**：每个部门有独立知识库、部门管理员、责任人与评估数据；部门之间默认隔离，公开知识全校可见。
2. **移动端可用**：普通用户通过手机浏览器或企业微信/钉钉入口完成登录、选库、问答、看引用、提反馈、转人工的完整流程。
3. **热点问题更快**：公开且稳定的高频问题命中缓存，响应明显加快；文档更新、废止、权限变化后缓存不返回旧答案。
4. **复杂问题可深度分析**：深度问答作为可选策略接入，最多 3 轮决策，展示决策轨迹，且每次检索都受 ACL 与版本过滤约束。
5. **运营可量化**：管理端能看待处理反馈、零引用率、转办率、缓存命中率、P95、部门使用情况与知识缺口。
6. **知识治理可持续**：文档到期复核提醒、知识缺口清单、部门评估报告形成闭环。
7. **企业入口可选**：学校具备条件时接入 CAS / 企业微信 / 钉钉登录与消息通知；不具备条件时独立 H5 可用。
8. **阶段二不回归**：ACL、版本、结构化分块、引用、评估、转办能力保持有效。

### 2.2 本阶段不做

- 不做原生 iOS / Android 应用；只做 H5 与企业微信/钉钉内嵌。
- 不做全校所有部门一次性上线；按部门 readiness 分批接入。
- 不做跨部门内部文档联合检索；用户只能检索公开库与本部门库，跨部门内部文档默认隔离。
- 不做学籍、成绩、一卡通、财务等跨系统数据打通。
- 不做自动审批、自动处分、自动认定等替代人工决策的能力。
- 不做模型训练、微调、私有化大模型训练平台。
- 不做多租户 SaaS、跨学校部署。
- 不默认开放 `admin_only` 文档问答；如确需开放，必须另行完成本地模型与合规评审。
- 不做语义缓存的默认全量开启；语义缓存必须可关闭、可审计、可清理。
- 不做 7×24 小时人工客服；转办仍由部门工作时间处理。
- 不做图片问答、语音问答、数字人。

### 2.3 前置条件

本阶段开始前，阶段二必须完成：

1. 文档级 ACL 与检索层过滤通过验收，越权召回为 0。
2. 文档生命周期、版本、生效/废止、增量重建可用。
3. 结构化分块、父子块、引用版本与免责声明可用。
4. 黄金测试集、基线与回归流程可用。
5. 人工转接与反馈扩展现可用。
6. 阶段一登录、双前端、权限、审计不回归。

未满足上述条件时，不得直接开始阶段三；应先补齐阶段二，避免在不可信的数据上叠加缓存、Agent 和移动端。

## 三、总体方案

### 3.1 目标形态

```text
入口层
  PC 管理端（admin / dept_admin）
  PC 用户端（student / staff）
  移动 H5（student / staff）
  企业微信 / 钉钉工作台（可选）
        ↓
认证与会话
  本地账号 + AuthProvider（cas / wecom / dingtalk）
        ↓
用户端
  知识库选择：全校公开库 + 本部门库
  问答策略：快速问答（默认）/ 深度问答（可选）
        ↓
缓存层（仅快速问答）
  精确缓存 + 可选语义缓存
  按权限范围与索引版本隔离
        ↓
检索层
  RetrievalScope（阶段二）
  向量 / BM25 前置 ACL 与版本过滤
  RRF → 精排 → 父块回填
        ↓
生成层
  快速问答：固定管道
  深度问答：Agent 循环，最多 3 轮
        ↓
答案与引用
  版本、条款、页码、免责声明、反馈/转办
        ↓
运营层
  看板、评估、知识缺口、复核提醒、审计
```

### 3.2 核心原则

1. **默认快速，深度可选**：高频单跳问题走固定管道；只有多跳、跨文件、用户主动选择时才进入 Agent，避免延迟与成本翻倍。
2. **权限继承，不得绕过**：缓存、Agent、移动端、企业入口都只能调用同一套 `RetrievalScope` 与检索服务，不得各自实现过滤。
3. **缓存不跨权限**：缓存键必须包含权限范围与索引版本；命中后仍要复核文档有效性。
4. **部门自治，平台兜底**：部门管理员管理本部门内容；系统管理员负责部门、公共库、模型、全局策略与审计。
5. **移动端只做用户端**：管理端仍以 PC 为主；用户端移动优先，不加载管理页面代码。
6. **先测量再优化**：缓存、GPU、Agent 的效果必须用基线、压测和评估证明，不能凭感觉上线。
7. **可降级**：缓存、模型、Agent、企业入口任一不可用时，核心问答与引用仍可用。

### 3.3 参考资产

| 参考项目 | 可复用内容 | 使用方式 |
| --- | --- | --- |
| `agent/` | `backend/src/agent/loop.py`、`state.py`、`tools.py`、`prompts.py` | 复制到本项目后改造，接入阶段二 ACL、版本与模型配置 |

## 四、多部门知识库治理

### 4.1 部门与知识库归属

1. 部门主数据沿用阶段二 `departments` 表，本阶段增加部门管理员、联系方式、状态与排序。
2. 知识库新增：
   - `department_id`：归属部门；全校公开库可为空。
   - `visibility`：`public` / `department`。
   - `owner_user_id`：部门责任人。
   - `review_cycle_days`：默认复核周期，例如 180 天。
   - `status`：active / disabled。
3. 公开库由系统管理员创建；部门库由部门管理员创建，系统管理员可代建。
4. 一个部门可以有多个知识库，例如「教务处制度库」「教务处办事指南」；用户端按知识库名称展示。
5. 知识库删除前必须确认无在用文档、无未办结转办；删除进入软删除或归档，不物理清空审计记录。

### 4.2 角色与数据范围

阶段二已有 `admin / dept_admin / staff / student`。本阶段明确部门管理员范围：

| 角色 | 本阶段范围 |
| --- | --- |
| `admin` | 全部部门、公开库、部门库、用户、模型、缓存、评估、审计 |
| `dept_admin` | 本部门知识库、文档、版本、反馈、转办、评估报告；不能创建公开库，不能管理其他部门 |
| `staff` | 公开库 + 本部门库问答；查看本人会话与反馈 |
| `student` | 公开库问答；查看本人会话与反馈 |

要求：

1. 部门管理员的数据范围由 `user.department_id` 决定，不能通过前端参数切换部门。
2. 系统管理员可以切换「当前管理部门」视图，但切换记录审计，不改变账号归属。
3. 部门管理员不能把自己提升为系统管理员，不能修改其他部门用户。
4. 一个用户只能属于一个主部门；如需兼职多部门，本阶段不做，使用系统管理员账号或后续扩展。

### 4.3 用户端知识库路由

1. 用户登录后，知识库列表由后端按 ACL 返回：
   - `student`：全部 `public` 知识库。
   - `staff`、`dept_admin`：全部 `public` 知识库加本部门 `department` 知识库。
   - `admin`：全部 `public` 与 `department` 知识库，用于排障与代管；正常问答仍按所选知识库执行。
2. 一次问答选择一个知识库；默认选择上次使用的可用库，否则选择公开库。
3. 用户切换知识库时，清空当前检索上下文，避免跨库引用混淆；会话仍保留，但消息标注所属知识库。
4. 知识库不可用、被停用、无文档时，前端给出空态，不自动回退到其他部门库。
5. 不提供跨部门内部文档联合检索；如用户问题涉及其他部门，提示其联系对应部门或使用公开库。
6. 系统管理员可以在管理端跨部门检索与预览，但正常问答仍按当前选择的知识库与 ACL 执行。

### 4.4 部门接入流程

每个部门按以下清单接入，未完成不得开放：

| 步骤 | 内容 | 责任方 | 交付物 |
| --- | --- | --- | --- |
| 1 | 指定部门责任人与部门管理员 | 部门负责人 | 责任人名单、管理员账号 |
| 2 | 盘点制度与办事指南 | 部门 | 文档清单、版本、生效日期 |
| 3 | 确认公开/内部范围 | 部门 + 信息中心 | 文档可见性清单 |
| 4 | 创建部门知识库 | 系统管理员/部门管理员 | 知识库 |
| 5 | 上传、解析、发布文档 | 部门管理员 | 已发布文档与入库报告 |
| 6 | 建立部门测试集 | 部门 + 评估负责人 | 至少 30 到 50 条部门题 |
| 7 | 跑基线并修复问题 | 项目组 | 部门基线报告 |
| 8 | 试运行与培训 | 部门 | 试运行记录、培训材料 |
| 9 | 正式开放 | 信息中心 | 开放通知、责任人、复核周期 |

要求：

1. 没有责任人与复核周期的部门不得开放。
2. 没有测试集的部门不得开放；可先用部门高频问题构建小测试集，再逐步扩展。
3. 开放前必须通过越权、过期版本、引用正确性检查。
4. 部门上线后每月至少看一次使用与反馈数据；每季度至少复核一次文档有效期。

### 4.5 部门治理指标

| 指标 | 说明 |
| --- | --- |
| 文档覆盖率 | 已发布文档数 / 部门应公开文档清单 |
| 文档过期率 | 超过复核日期未处理的文档占比 |
| 零引用率 | 无有效引用的回答占比 |
| 转办率 | 转人工/转部门的问题占比 |
| 反馈处理时长 | 首次响应、办结时间 |
| 测试集通过率 | 部门测试集的 Recall、引用正确率、拒答正确率 |
| 使用量 | 日/周提问量、活跃用户、知识库分布 |

### 4.6 数据模型扩展

在阶段二基础上增加：

- `knowledge_bases.department_id`、`visibility`、`owner_user_id`、`review_cycle_days`、`status`。
- `departments.contact`、`sort_order`、`status`。
- `users.department_id` 已存在；增加 `is_department_admin` 可省略，角色已表达。
- `auth_identities`（可选）：外部身份源、外部用户 ID、本地用户 ID、绑定时间。
- `notification`（可选）：通知类型、接收人、渠道、状态、发送时间。

## 五、移动端 H5

### 5.1 定位

1. 移动端只服务普通用户与管理员的用户端问答，不承载管理端。
2. 复用同一套 Vue 用户端代码，通过响应式布局与 `VITE_APP_MODE=user` 构建，不新建第二套前端工程。
3. 管理端保持 PC 布局；移动端不加载管理页面代码、不展示管理菜单。
4. 企业微信/钉钉入口是可选外壳，底层仍是同一 H5 与同一后端。

### 5.2 页面与流程

移动端必须覆盖：

| 页面/能力 | 要求 |
| --- | --- |
| 登录 | 用户名密码；企业入口可选 SSO；错误提示不泄露账号是否存在 |
| 问答 | 选知识库、输入问题、流式回答、停止生成、重新生成（可选） |
| 引用 | 引用卡片/抽屉展示文件名、页码、条款、版本、生效日期、责任部门、片段 |
| 历史会话 | 会话列表抽屉；新建、切换、删除自己的会话 |
| 反馈 | 答案下反馈按钮；类型、描述、期望答案、联系方式；提交后显示工单号 |
| 转人工 | 无引用/拒答/用户主动求助时出现；显示转办号与状态 |
| 我的反馈 | 状态、管理员回复、时间线；只显示本人 |
| 个人菜单 | 修改密码、退出、返回管理端（仅管理员） |

移动端明确禁止：

- 知识库创建/编辑/删除、文档上传/入库/发布/废止。
- 模型选择、检索策略参数配置、日志、用户管理、反馈处理、评估。
- 查看他人会话或他人反馈。

### 5.3 交互与布局

1. 适配宽度：360、390、414、430 像素；最低 360 像素不出现横向滚动。
2. 触控目标不小于 44×44 像素；按钮、引用卡片、会话项易于点击。
3. 输入框固定在底部，适配 iOS 安全区与软键盘；键盘弹出时消息流不被遮挡。
4. 引用使用底部抽屉或全屏子页，不挤压消息区域；关闭后回到原滚动位置。
5. 流式回答时保持自动滚动到底部，但用户上滑后停止自动滚动；提供「回到底部」。
6. 长回答、长引用、Markdown 表格在窄屏可横向滚动或折叠，不撑破页面。
7. 深色模式跟随系统或用户偏好；移动端保持与 PC 一致的视觉语言。
8. 网络中断、超时、401、403、429、500 有明确提示与重试；不展示后端堆栈。

### 5.4 性能与体验

1. 用户端按路由懒加载；管理端代码不进入用户端构建产物。
2. 首屏只加载登录/问答必要资源；引用组件、历史抽屉按需加载。
3. 流式回答首字时间优先；模型预热期间显示「正在准备」而不是空白。
4. 图片、图标压缩；避免大图阻塞首屏。
5. 建议目标：4G 网络下首屏可交互不超过 3 秒，具体以压测为准。
6. 提供骨架屏、空态、错误态、加载态，避免白屏。
7. 移动端不做复杂检索详情调试面板；用户只看引用与简要检索信息。

### 5.5 企业微信/钉钉入口（条件项）

学校选定后实施：

1. OAuth 登录：跳转授权、回调校验、`state` 防重放、票据校验。
2. 用户映射：企业用户 ID / 工号 / 学号映射到本地用户；首次登录可自动创建待激活账号或绑定已有账号。
3. 部门映射：企业通讯录部门映射到本地部门；映射失败进入待分配，不默认开放内部文档。
4. 角色映射：管理员/教职工/学生按组织属性映射；保留本地管理员兜底账号。
5. 工作台入口：配置应用主页为 H5 地址；域名白名单、可信域名、JS-SDK 签名（如使用）。
6. 消息通知：反馈/转办状态变更可发送企业消息；未配置时只用站内通知。
7. 安全：密钥只放后端环境变量；前端不持有企业 secret；回调地址白名单；令牌不写日志。
8. 如果学校没有企业微信/钉钉，提供独立 H5 地址与二维码，不阻塞上线。

### 5.6 验收设备

至少覆盖：

- iOS Safari 最近两个大版本。
- Android Chrome 最近两个大版本。
- 企业微信内置浏览器（如接入）。
- 钉钉内置浏览器（如接入）。
- 360×640、390×844、430×932 三种视口。
- 弱网/断网、键盘弹出、横竖屏切换。

## 六、热点问题缓存

### 6.1 适用范围

1. 只缓存快速问答（固定管道）的成功答案。
2. 不缓存深度问答、拒答、转人工、无引用、引用越界、包含个人信息的回答。
3. 不缓存 `admin_only` 文档相关回答。
4. 公开知识库可跨用户共享缓存；部门内部知识库按部门与角色范围隔离。
5. 缓存命中后仍必须执行权限与版本复核；复核失败直接回源，不得返回缓存。

### 6.2 缓存键

缓存键至少包含：

```text
kb_id
strategy_id
scope_fingerprint = hash(role, department_id, allowed_visibility)
index_epoch = 知识库索引版本号
normalized_question_hash
```

要求：

1. 问题归一化：去首尾空白、统一全半角、合并连续空白、统一大小写（英文）；不改变语义。
2. `index_epoch` 在文档发布、废止、ACL 变更、分块策略变更、知识库重建时递增；旧键自然失效。
3. 不允许只用问题文本做键，避免跨知识库、跨权限、跨版本串答案。
4. 允许同一用户在同一范围重复提问命中；不同部门默认不共享内部库缓存。
5. 缓存键与值不包含明文密码、令牌、完整个人信息。

### 6.3 精确缓存与语义缓存

| 类型 | 默认 | 说明 |
| --- | --- | --- |
| 精确缓存 | 开启 | 归一化问题哈希完全一致才命中；安全、可预测 |
| 语义缓存 | 关闭，可选 | 问题向量相似度达到阈值才命中；必须同范围、同版本、同策略 |

语义缓存要求：

1. 默认关闭，由系统管理员按知识库开启。
2. 相似度阈值建议不低于 0.95，最终值用测试集校准；低于阈值的近似问题不得命中。
3. 只对公开库、稳定制度问答开启；部门内部库默认关闭。
4. 命中后必须展示「相似问题」来源或缓存标识，便于用户判断。
5. 语义缓存命中也要复核引用文档仍然有效、用户仍有权限。
6. 语义缓存误答进入反馈时，必须能定位缓存键、相似问题、原始答案与版本，支持清理。
7. 语义缓存实现不得引入新的向量库；复用现有嵌入模型与缓存索引，或使用 Redis 向量能力；具体选型在实施前评审。部署环境不具备 Redis 向量能力时不得开启语义缓存，精确缓存不受影响。

### 6.4 TTL 与失效

1. 精确缓存 TTL 建议 7 天；可按知识库配置 1 到 30 天。
2. 语义缓存 TTL 建议不超过 3 天，并随 `index_epoch` 失效。
3. 以下事件必须使相关缓存失效：
   - 文档发布、废止、归档、回滚。
   - 文档可见性、归属部门、版本生效日期变化。
   - 知识库启停、删除、分块策略变化。
   - 检索策略预设变化。
   - 管理员手动清理。
4. 失效方式优先使用 `index_epoch` 递增，使旧键不再命中；后台异步清理旧键，避免阻塞发布。
5. 缓存服务不可用时，问答直接回源，不阻断主流程。

### 6.5 缓存内容

缓存值至少包含：

```text
answer
citations
strategy_id
strategy_name
kb_id
index_epoch
document_versions
created_at
expires_at
disclaimer
```

要求：

1. 引用必须保留版本、页码、条款、生效日期；命中缓存不能丢失引用。
2. 缓存答案不得拼接用户个人信息或会话上下文。
3. 缓存命中页面可以标注「热点问题缓存」，也可以不标注；后台必须可追踪。
4. 缓存值不存储用户 ID、会话 ID、反馈内容；如需统计，只存匿名计数。

### 6.6 安全

1. 缓存键包含权限范围，禁止跨角色/跨部门命中。
2. 命中后重新校验用户状态、角色、部门、文档可见性、版本有效性；任一失败回源。
3. 缓存写入前校验引用：至少一条有效引用、无越界引用、文档属于当前索引版本。
4. 防止缓存投毒：只允许后端写缓存；管理端清理需要 `admin` 权限并审计。
5. Redis 不暴露公网；启用访问控制；不存明文敏感信息。
6. 语义缓存相似问题不得包含无权文档标题或片段。

### 6.7 管理端

新增缓存管理：

- 缓存开关（全局、按知识库）。
- 精确/语义缓存开关与阈值。
- TTL 配置。
- 命中率、平均回源耗时、缓存节省耗时、旧版本命中次数。
- 按知识库清理、按文档清理、全量清理。
- 语义缓存样本查看与误答标记（脱敏）。
- 清理与开关变更审计。

### 6.8 验收指标

- 缓存命中率：试运行两周后，公开库高频问题建议达到 30% 以上。
- 缓存命中 P95：相对回源明显下降，建议至少下降 50%，最终以压测为准。
- 旧版本命中次数 = 0。
- 越权缓存命中次数 = 0。
- 文档发布/废止后 1 分钟内不再返回旧答案。

## 七、深度问答 Agent

### 7.1 定位

1. 深度问答是用户端的一种可选策略，不是默认路径，也不是第二套系统。
2. 适用于多跳、跨文件、需要组合依据的问题；单跳高频问题继续走快速问答。
3. 深度问答复用本项目后端、账号、知识库、ACL、版本、引用、反馈与评估，不新建第二套后端或账号。
4. 管理端可配置是否对用户开放、对哪些知识库开放、对哪些角色开放；默认关闭，试运行后按部门开启。
5. 深度问答不进入热点缓存；每次请求独立决策。

### 7.2 决策循环

复用 `agent/` 的三轮收敛设计，适配本项目：

```text
意图识别：正常交流 / 知识库问答
  ↓
第 1 轮：改写 query、选择策略、检索；歧义则反问
  ↓
第 2 轮：评估证据；不足则换角度再检索（禁止完全相同 query）
  ↓
第 3 轮：必须直接作答，不再调用工具
  ↓
输出答案 + 引用 + 决策轨迹
```

硬约束：

1. 单问题最多 3 轮决策，第 3 轮必须收敛。
2. 最多 3 次检索工具调用；用尽即强制作答。
3. 每轮最多一个工具调用；只允许 `retrieve` 与 `ask_clarification`，不开放任意工具。
4. 未检索前不得凭记忆回答知识库问题；保留检索优先守卫。
5. 触顶、未知工具、空 query、异常时追加「必须作答」指令，禁止无限循环。
6. 深度问答失败时回退快速问答，并向用户说明「已切换快速问答」；不得返回半成品或伪造引用。

### 7.3 接入方式

1. 复制 `agent/backend/src/agent/` 到本项目 `backend/src/agent/`，保留 `loop.py`、`state.py`、`tools.py`、`prompts.py` 的职责划分。
2. 复用本项目 `services/chat_service.py` 的会话、消息、SSE、日志能力；新增 `services/agent_service.py` 作为门面。
3. 新增 `/api/v1/agent/chat` 与 `/api/v1/agent/chat/stream`，或复用 `/chat/stream` 并通过 `strategy_id=deep` 路由；推荐后者，减少前端分支。
4. SSE 事件协议：
   - `meta`：会话 ID、是否 Agent。
   - `agent_step`：意图、检索、澄清、强制作答等步骤。
   - `delta`：答案增量。
   - `done`：最终答案、引用、轨迹、耗时。
   - `error`：可读错误，不返回堆栈。
5. 轨迹持久化到消息 `latency.agent_trace`，历史会话可还原；轨迹不包含完整系统提示与密钥。
6. 前端不直接调用 Agent 内部接口；统一走用户端问答接口。

### 7.4 ACL 与版本约束

1. Agent 的每次 `retrieve` 必须携带当前 `RetrievalScope`，由后端服务注入，不接受模型参数。
2. 检索工具只能调用阶段二的检索服务，不能绕过 ACL、版本、生效日期过滤。
3. Agent 不能扩大知识库范围；用户选择一个库，Agent 只能在该库内检索。
4. Agent 不能读取 `admin_only` 文档；本阶段该类文档仍不进入索引。
5. Agent 累积证据必须按 `chunk_id` 去重；引用只来自有权、当前有效文档。
6. 任何越权、过期、旧版本引用都视为验收失败；不得用「模型不知道权限」作为解释。
7. 检索结果进入 Prompt 前标记为「资料」，系统提示明确要求忽略资料中的指令，防止文档注入。

### 7.5 模型与生成

1. 深度问答默认使用与快速问答相同的生成模型配置，避免两套模型密钥与计费。
2. 支持在线 OpenAI 兼容接口；如学校已有本地模型，可作为可选通道接入。
3. 模型路由按知识库配置：公开库可走云端；部门内部库是否允许云端由学校合规确认；`admin_only` 默认仍不进入问答，如确需开放，按 2.2 另行完成本地模型与合规评审。
4. 本地模型接入作为条件项，不在本阶段硬性验收；未接入前不得开放敏感文档问答。
5. 决策温度默认 0，保证稳定；最大 token、超时、重试次数可配置。
6. 单次深度问答设置总超时与 token 预算；超时回退快速问答或返回可读错误。
7. 不让模型直接访问数据库、文件系统、网络或任意工具。

### 7.6 用户端交互

1. 问答输入区提供「深度问答」开关或策略选择；默认关闭。
2. 开关只在管理员开放且当前知识库支持时显示；未开放时不显示。
3. 回答过程中展示「正在分析」「正在检索」「正在整理依据」等状态，不展示内部 Prompt。
4. 回答完成后可展开「决策轨迹」：意图、每轮 query、策略、命中条数、耗时、是否强制作答。
5. 轨迹中的文档片段只展示用户有权查看的内容；无权文档不出现。
6. 深度问答回答同样展示引用、版本、免责声明、反馈与转人工入口。
7. 深度问答失败回退快速问答时，明确提示，不静默切换。
8. 移动端轨迹使用底部抽屉或折叠面板，不挤压消息区。

### 7.7 限流与成本

1. 深度问答按用户与知识库限流，建议低于快速问答；具体阈值由试运行确定。
2. 记录每次请求的轮数、检索次数、token、耗时、是否回退；进入运营看板。
3. 对高频重复问题，优先引导快速问答或缓存；深度问答不缓存。
4. 成本异常（token 激增、轮数偏高）告警，管理端可临时关闭深度问答。
5. 深度问答开放按部门灰度：先管理员与部门管理员，再教职工，最后学生（如开放）。

### 7.8 评估

1. 在黄金测试集中增加多跳、跨文件、需要组合依据的题目。
2. 对比快速问答与深度问答：答案正确率、引用正确率、忠实度、P95、平均轮数、token。
3. 硬门槛：越权引用 0、旧版本引用 0、轮数不超过 3、工具调用不超过 3。
4. 软门槛：多跳题正确率不低于快速问答；整体延迟不高于快速问答的 2 倍；具体阈值评审确认。
5. 深度问答不得拉低快速问答指标；两者分别统计，不混在一起。

## 八、企业入口、统一认证与通知（条件项）

### 8.1 适用条件

学校在实施期内提供以下信息时启用：

- 认证方式：CAS / 企业微信 / 钉钉。
- 应用凭证、回调地址、可信域名。
- 用户与组织属性映射规则。
- 测试账号与测试部门。

未提供时：

- 继续使用本地账号密码。
- 提供独立 H5 地址与二维码。
- 通知只做站内。

### 8.2 登录与账号映射

1. 认证层复用阶段一 `AuthProvider` 抽象，新增 `cas`、`wecom`、`dingtalk` 实现。
2. OAuth 流程必须校验 `state`、回调地址、票据/授权码；失败不建立会话。
3. 首次登录按外部唯一 ID 查找本地账号：
   - 已绑定：直接登录。
   - 未绑定但能匹配学号/工号：绑定并登录。
   - 无法匹配：进入待激活/管理员审核，不自动授予内部文档权限。
4. 角色与部门映射：
   - 学生 → `student`。
   - 教职工 → `staff`。
   - 部门管理员由本地管理员指定，不直接信任外部属性。
   - 系统管理员保留本地兜底账号。
5. 外部身份源故障时，本地管理员账号仍可登录；普通用户可切换本地登录（如允许）。
6. 解绑、离职、转部门：下一次登录或下一次请求生效；必要时撤销会话。

### 8.3 通知

1. 站内通知默认开启：反馈回复、转办状态、待处理提醒。
2. 企业微信/钉钉通知为可选：
   - 反馈已受理/已回复/已办结。
   - 转办待处理、超时提醒。
   - 文档到期复核提醒（管理员）。
3. 通知内容不包含完整问答正文、个人信息、密钥；只包含工单号、状态、跳转链接。
4. 通知失败不回滚业务状态；记录失败原因并重试。
5. 用户可关闭非必要通知；管理员通知不可关闭或由系统配置。

### 8.4 安全

1. 企业 secret、私钥只放后端环境变量；前端不持有。
2. 回调地址白名单；`state` 一次性；授权码/票据不写日志。
3. 外部用户属性不可直接作为本地角色；必须经过映射与审核。
4. 通知链接使用短期令牌或登录态校验，不把敏感信息放 URL。
5. 企业入口与本地入口共用同一会话与权限模型，不新建第二套账号。

### 8.5 验收（条件项）

- [ ] 授权跳转、回调、登录成功，失败场景有可读提示。
- [ ] 外部用户正确映射到本地用户、部门、角色。
- [ ] 无法匹配的用户进入待审核，不自动获得内部权限。
- [ ] 本地管理员兜底账号可登录。
- [ ] 通知可送达，失败有记录，不阻断业务。
- [ ] 密钥不在前端、日志、仓库中出现。

## 九、运营看板与知识缺口

### 9.1 看板指标

管理端新增 `/admin/dashboard`：

| 指标 | 说明 |
| --- | --- |
| 今日/近 7 日提问量 | 按知识库、部门、角色统计 |
| 活跃用户 | 日活、周活；不展示个人敏感行为 |
| 零引用率 | 无有效引用的回答占比 |
| 拒答率 | 明确拒答占比 |
| 转办率 | 转人工/转部门占比 |
| 反馈率 | 有反馈的回答占比 |
| 反馈办结时长 | 首次响应、平均办结 |
| 缓存命中率 | 精确/语义分别统计 |
| P50/P95 延迟 | 检索、精排、生成、总耗时 |
| 错误率 | 4xx/5xx、模型失败、索引失败 |
| 文档过期数 | 超过复核日期的文档 |
| 部门对比 | 各部门提问量、零引用率、转办率、测试集通过率 |

要求：

1. 指标按权限过滤：`dept_admin` 只看本部门；`admin` 看全部。
2. 聚合数据不展示用户问题原文，除非进入具体工单且有权限。
3. 指标口径固定并在页面说明；避免同一指标多种算法。
4. 数据延迟可接受分钟级；不要求实时。
5. 图表与表格均可导出 CSV；导出审计。

### 9.2 知识缺口分析

1. 汇总零引用问题、拒答问题、负反馈、转办问题，按语义聚类。
2. 每个缺口展示：问题样本（脱敏）、出现次数、知识库、最近出现时间、关联反馈/转办。
3. 支持标记：待补文档、文档过期、检索问题、模型问题、无需处理。
4. 支持分配给部门管理员，形成待办；处理后可关联新文档或版本。
5. 支持导出缺口清单，供部门月度治理会使用。
6. 聚类可以使用嵌入模型，但不得把无权文档内容混入；只处理公开/本部门范围。

### 9.3 文档复核提醒

1. 每日定时扫描 `review_due_date`：
   - 提前 30 天提醒。
   - 到期当天提醒。
   - 逾期后每周提醒，直到处理。
2. 提醒对象：文档责任人、部门管理员；系统管理员看汇总。
3. 管理端导航显示角标；站内通知默认；企业通知可选。
4. 责任人可以「确认继续有效」「发起修订」「废止」；操作写审计。
5. 逾期文档不自动下线，但看板标红；是否自动降权由部门确认。

### 9.4 报告

1. 周报：提问量、零引用、转办、缓存、P95、异常。
2. 月报：部门对比、知识缺口、文档过期、测试集回归。
3. 报告导出 Markdown/CSV；敏感内容脱敏。
4. 评估报告与运营报告分开，不混用指标。

### 11.5 缓存

缓存不建业务表，使用 Redis：

- 键：`cache:{kb_id}:{strategy}:{scope_hash}:{epoch}:{question_hash}`。
- 值：JSON，包含答案、引用、版本、策略、时间、免责声明。
- 统计：命中/未命中计数器，按知识库与日期聚合。
- 语义缓存索引：单独前缀，记录问题向量与缓存键映射；不存用户 ID。

### 11.6 运营指标

可以使用现有检索日志、消息、反馈、审计表聚合；如性能不足，增加 `metrics_daily` 汇总表：

| `department_id` / `kb_id` | 维度 |
| `questions` | 提问量 |
| `active_users` | 活跃用户 |
| `zero_citation` | 零引用数 |
| `refusals` | 拒答数 |
| `transfers` | 转办数 |
| `cache_hits` | 缓存命中 |
| `p95_ms` | P95 |
| `errors` | 错误数 |

## 十三、验收标准

### 13.1 多部门治理

- [ ] 系统管理员可创建部门、指定部门管理员、创建公开库与部门库。
- [ ] 部门管理员只能看到并管理本部门知识库、文档、反馈、评估报告。
- [ ] 部门管理员访问其他部门资源返回 403/404。
- [ ] 学生只看到公开库；教职工看到公开库与本部门库；系统管理员可查看全部库；任何角色都看不到无权内部库。
- [ ] 用户端知识库列表由后端 ACL 返回，前端不能通过参数越权。
- [ ] 部门停用后，其知识库不再对用户展示，已有会话可读但新问答不可用。
- [ ] 部门接入清单完成，责任人与复核周期已登记。
- [ ] 跨部门越权召回 = 0，跨部门越权预览 = 0。

### 13.2 移动端 H5

- [ ] 360 像素宽度下无横向滚动，输入框、消息、引用、按钮可用。
- [ ] iOS Safari、Android Chrome、企业微信/钉钉内置浏览器（如接入）完成登录、选库、问答、引用、反馈、转办。
- [ ] 流式回答正常，停止生成可用，键盘弹出不遮挡输入框。
- [ ] 引用抽屉/子页可打开、关闭，返回后滚动位置保持。
- [ ] 历史会话可切换、删除；只能看到自己的会话。
- [ ] 用户端构建产物不包含管理页面代码与管理菜单。
- [ ] 弱网、断网、401、403、429、500 有明确提示与重试。
- [ ] 移动端不出现模型选择、知识库管理、文档入库、日志、用户管理、反馈处理。

### 13.3 热点缓存

- [ ] 精确缓存默认开启；语义缓存默认关闭，可配置。
- [ ] 缓存键包含知识库、策略、权限范围、索引版本；跨范围不命中。
- [ ] 缓存命中后仍校验权限与文档有效性；越权/过期/旧版本命中 = 0。
- [ ] 文档发布、废止、ACL 变更、策略变更后 1 分钟内不再返回旧答案。
- [ ] 缓存只保存有有效引用、无越界引用的答案；拒答、转办、深度问答不入缓存。
- [ ] 缓存不可用时问答正常回源，不阻断。
- [ ] 管理端可查看命中率、清理缓存、关闭缓存，操作有审计。
- [ ] 试运行两周公开库命中率达到约定目标，命中 P95 明显下降。

### 13.4 深度问答

- [ ] 深度问答默认关闭，按知识库/角色开启后可见。
- [ ] 单问题最多 3 轮、最多 3 次检索；第 3 轮强制作答。
- [ ] 每次检索携带当前用户 ACL 与版本范围；越权引用 = 0、旧版本引用 = 0。
- [ ] 决策轨迹展示意图、每轮 query、策略、命中数、耗时；历史会话可还原。
- [ ] 深度问答失败回退快速问答，有明确提示，不返回半成品。
- [ ] 深度问答不进入缓存；限流与 token 统计生效。
- [ ] 多跳题正确率不低于快速问答基线；延迟不超过约定倍数。
- [ ] 文档中的指令不能改变系统行为；工具仅限检索与澄清。

### 13.5 企业入口与通知（条件项）

- [ ] 如启用 CAS/企业微信/钉钉：授权、回调、映射、角色、部门、兜底账号全部通过。
- [ ] 外部用户无法匹配时进入待审核，不自动获得内部权限。
- [ ] 通知可送达；失败有记录、可重试、不阻断业务。
- [ ] 密钥不出现在前端、日志、仓库。
- [ ] 未启用企业入口时，独立 H5 与站内通知可用。

### 13.6 运营看板与知识缺口

- [ ] 看板指标口径明确，按权限过滤，部门管理员只看本部门。
- [ ] 提问量、零引用率、转办率、缓存命中率、P95 与实际日志一致（抽样核对）。
- [ ] 知识缺口可聚类、分配、标记、导出；处理后可关联文档。
- [ ] 文档到期提醒按 30 天/当天/逾期规则触发；责任人可确认、修订、废止。
- [ ] 周报/月报可导出，敏感信息脱敏。
- [ ] 看板与缺口数据不泄露用户隐私与无权文档。

### 13.7 性能、安全与回归

- [ ] 在约定并发下无 5xx；P95 达到评审目标。
- [ ] 缓存、深度问答、移动端均有降级方案。
- [ ] 跨部门、缓存、Agent、移动端安全用例通过。
- [ ] 阶段二 ACL、版本、结构化分块、引用、评估、转办全部回归通过。
- [ ] 阶段一登录、双前端、权限、反馈、审计全部回归通过。
- [ ] 项目仍位于 `基于langchain的校园rag知识库系统/`，不依赖 demo/product/agent。
- [ ] 注释符合 `SKILL.md`；未修改三版原项目文件。

## 十七、待确认事项

1. **部门上线顺序**：先教务处，还是同时接入学工、财务、图书馆；每部门责任人与文档清单。
2. **企业入口选型**：CAS、企业微信、钉钉还是不接入；应用凭证、回调地址、可信域名。
3. **移动端形态**：独立 H5、企业微信工作台、钉钉工作台；是否需要二维码入口。
4. **深度问答开放范围**：只管理员/教职工，还是学生也可用；按部门还是按知识库开放。
5. **缓存策略**：精确缓存 TTL；语义缓存是否开启、阈值、适用知识库。
6. **模型与算力**：云端模型是否允许部门内部文档；是否接入本地模型；GPU 资源。
7. **性能目标**：目标并发、P95、缓存命中率、深度问答延迟上限。
8. **通知渠道**：站内、企业微信、钉钉、邮件；哪些状态必须通知。
9. **看板指标口径**：零引用、拒答、转办、活跃用户的定义。
10. **知识缺口处理责任**：谁聚类、谁分配、谁验收；处理时限。
11. **文档复核规则**：提前多久提醒、逾期是否降权/下线。
12. **数据保留**：会话、反馈、审计、缓存、看板明细保留多久；如何归档。
13. **安全合规**：企业入口个人信息、日志脱敏、跨部门数据访问审批。

## 十八、与总方案、阶段一、阶段二的关系

- 本文件落实《项目落地方案.md》第三阶段「好用」：移动端、热点缓存、深度问答、多部门治理。
- 阶段一解决「可登录、可分权、可分端、可反馈」；阶段二解决「文档有权限、版本可追溯、引用可核验、质量可回归、问题可转办」；阶段三解决「多部门可治理、手机可用、热点更快、复杂问题可深度分析、运营可持续」。
- 阶段三不得绕过阶段二的 ACL、版本、引用与评估规则；缓存、Agent、移动端、企业入口都必须继承同一套权限与版本过滤。
- 深度问答是可选能力，不替代快速问答；缓存只服务快速问答；移动端只承载用户端；多部门治理不改变单部门内的权限模型。
- 阶段三完成不等于自动上线；是否投入使用按《上线准入标准.md》的 G1 到 G7 判定。
- 本阶段完成后，系统具备校园生产环境可持续运营的完整形态；后续如需扩展，应单独立项，不在本文件范围内。
