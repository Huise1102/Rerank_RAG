> 本文件是执行约束，不是需求文档。它规定智能体在落地本项目时必须遵守的边界、顺序、质量标准和交付形态。

> 需求以同目录的阶段文档（《阶段一.md》《阶段二.md》《阶段三.md》）和《项目落地方案.md》为准；本文件规定“怎么做、不能做什么、做到什么程度”。
>
> 编写日期：2026-11-13
>
> 适用对象：后续所有参与本项目的智能体会话，包括上下文压缩后恢复的会话。

## 一、项目定位与交付边界

### 1.1 项目定位

在仓库根目录新建独立项目文件夹：

```text
基于混合检索与Rerank的领域知识库系统/
├── demo/                      现有验证版，只读参考
├── product/                   现有产品版，行为参考，只读
├── agent/                     现有智能体版，只读参考
└── 基于LangChain的校园RAG知识库系统/          本项目，唯一允许写入的项目目录
```

`基于LangChain的校园RAG知识库系统/` 与 `demo/`、`product/`、`agent/` 三版并列，不是其中任何一版的子目录，也不是第四种演示形态。

本项目以 LangChain 作为检索与生成链路的统一框架，从零构建独立后端与前端。`product/` 只用于对照业务流程与交互形态，不复制其代码、配置、索引、模型缓存或启动脚本。本项目不依赖 `demo/`、`product/`、`agent/` 中的任何内容。

### 1.2 阶段交付边界

项目按《阶段一.md》《阶段二.md》《阶段三.md》分阶段推进。当前实现范围以用户明确指定的阶段文档为准；用户未指定时，默认只落地《阶段一.md》。

阶段一交付：

1. 统一身份认证与用户角色。
2. 管理端与 PC 用户端双前端；阶段三新增移动端。
3. 后端真实鉴权与资源归属隔离。
4. 用户问答、策略自选、引用查看、历史会话。
5. 用户反馈提交、我的反馈、管理端反馈处理闭环。
6. 登录审计、管理操作审计、限流与基础安全加固。
7. 独立数据库、独立配置、独立依赖、独立启动与验收。

阶段二、阶段三的需求已分别写入同目录文档，未进入对应阶段并获得用户确认前，不得提前实施。进入后续阶段时，以对应阶段文档和用户确认的里程碑为准，本文件的硬性约束继续有效。

### 1.3 文档优先级

出现冲突时，按以下顺序处理：

1. 用户在对话中的明确指令。
2. 本文件中的硬性约束。
3. 当前阶段文档的阶段目标、权限矩阵和验收标准。
4. 《项目落地方案.md》的总体方案。
5. `product/` 现有实现与行为。

如果低优先级内容与高优先级内容冲突，不得自行取舍，应停止相关改动并向用户说明冲突点，等待确认。

### 1.4 文档中的旧路径如何理解

《阶段一.md》《阶段二.md》《阶段三.md》和《项目落地方案.md》中的 `product/backend/...`、`product/frontend/...` 等路径，表示迁移来源和改造落点，不是本项目的目标路径。迁移到本项目后，统一按下表映射：

| --- | --- |
| `product/backend/` | `基于LangChain的校园RAG知识库系统/backend/` |
| `product/frontend/` | `基于LangChain的校园RAG知识库系统/frontend/` |
| `product/resource/` | `基于LangChain的校园RAG知识库系统/resource/`，只复制实际需要的语料 |

| `product/backend/src/core/config.py` | `基于LangChain的校园RAG知识库系统/backend/src/core/config.py` |

### 1.5 阶段文档索引

## 二、硬性约束

以下约束不可协商。除非用户明确书面豁免，任何一条不满足都视为交付不合格。

### H1 单个智能体完成，不得私自开子智能体

1. 本项目从迁移、改造、测试到验收，由一个智能体连续完成。
2. 禁止调用 `subagent` 工具，禁止创建探索代理、通用代理、后台代理、并行子会话，禁止把任务拆给其他智能体。
3. 禁止通过脚本、Code Mode、外部服务或其他方式变相委托给第二个智能体。
4. 只有用户在当前对话中明确说“允许使用 subagent”或等价表述，才视为授权；沉默、默认、历史授权、“你看着办”均不构成授权。
5. 授权只对当次任务有效，必须限定任务范围、文件和产出；子智能体的结果必须由主智能体逐项复核后才能采用。
6. 任务量大时，智能体应自行拆成里程碑顺序执行，而不是开子智能体并行。上下文不足时，先读文件和整理笔记，再继续。

### H2 所有项目内容只能放在 `基于LangChain的校园RAG知识库系统/` 内

1. 新增的源码、配置、依赖清单、脚本、测试、文档、示例数据、运行产物，全部位于本项目文件夹内。
2. 不得在仓库根目录新增其他文件或文件夹；不得在 `demo/`、`product/`、`agent/` 内新增、修改、删除任何内容。
3. 不得使用符号链接、目录联接、Git 子模块等方式引用父目录中的代码、数据或依赖。
4. 临时脚本和临时数据优先放在项目内被忽略的目录，或系统临时目录，完成后清理；不得散落在仓库根目录。
5. 本项目文件夹本身不得再嵌套一个同名项目目录，例如不得出现 `基于LangChain的校园RAG知识库系统/基于LangChain的校园RAG知识库系统/`。

### H3 项目必须能脱离主文件夹独立运行

1. 项目要有自己的 `.env`、`.env.example`、后端依赖清单、前端依赖清单与锁文件、全局配置、数据库迁移、启动脚本、健康检查、测试和 README。
2. 运行时不得读取父目录的 `.env`、`.venv`、`node_modules`、`.hf-cache`、`.uv-cache`、`resource/` 或任何父级配置。
3. 不得出现 `../product`、`../demo`、`../agent`、`..\\product` 等跨项目引用。
4. 不得出现个人电脑绝对路径，例如 `C:\Users\...`、`D:\...`；所有路径必须由项目根目录推导或来自环境变量。
5. 把 `基于LangChain的校园RAG知识库系统/` 单独复制到仓库外的目录后，按 README 重新安装依赖、准备 `.env`、初始化数据库，即可启动。验收时必须实际验证或如实说明未验证项。

### H4 现有三版只读，不得破坏

1. `demo/`、`product/`、`agent/` 只用于阅读、对比和复制必要文件。
2. 不得修改、移动、删除三版中的代码、配置、数据、文档或运行产物。
3. 不得把三版的 `.env`、`.venv`、`node_modules`、`dist`、`__pycache__`、索引、上传文件、日志复制进本项目。
4. 需要复制语料、模型配置或代码片段时，只复制必要部分，并在本项目内改写为独立路径。
5. 如需修改仓库根目录的共享文件（例如 `start_all.py`、`README.md`、`SKILL.md`），必须先征得用户同意。

### H5 不擅自扩大或缩小需求

1. 只实现当前阶段文档明确要求的能力；后续阶段内容未获用户确认前不得提前实施。
2. 不得以“顺便优化”为由重写检索链路、替换技术栈、改造 UI 风格或引入当前阶段未要求的新中间件。
3. 不得删除现有可用功能来换取实现方便；管理端问答、知识库、检索策略、日志等能力不得回归。
4. 需求缺失或存在歧义时，先提出具体问题；不要用猜测填补关键业务规则，尤其是权限、角色、数据归属和反馈状态流转。

### H6 安全底线

1. 密码必须使用 bcrypt、argon2 等慢哈希存储，禁止明文、MD5、SHA1。
2. 不得在代码、文档、日志、提交记录中写入真实密钥、数据库口令、初始管理员明文密码。
3. `.env` 必须被 `.gitignore` 忽略；仓库只保留占位值的 `.env.example`。
4. 所有管理接口必须在后端校验 `admin` 角色，不能只靠前端隐藏菜单。
5. 会话、消息、反馈等资源必须校验归属，禁止仅凭 ID 查询他人资源。
6. 用户 ID、角色、部门必须从登录态解析，不得信任请求体、查询参数或前端存储中的身份字段。
7. 生产配置必须支持 HTTPS、CORS 白名单、登录限流、XSS 防护和日志脱敏。

### H7 禁止破坏性操作

1. 禁止 `git reset --hard`、`git clean -fd`、强制推送、批量删除未确认文件。
2. 禁止对现有数据库执行 `DROP DATABASE`、清空表、覆盖生产数据。
3. 禁止删除或覆盖用户已有的 `.env`、文档、截图、数据文件。
4. 需要执行不可逆操作时，先说明影响并获得用户明确同意。
5. 发现工作区有未提交改动时，先判断是否为用户正在进行的工作；不得擅自回滚。

### H8 未经运行验证不得宣称完成

1. 不得用“应该可以”“理论上没问题”代替实际验证。
2. 每个里程碑至少完成：后端可导入、数据库迁移可执行、相关接口可调用、前端可构建。
3. 交付前必须跑通阶段一的关键路径：管理员登录、普通用户登录、用户问答、引用展示、反馈提交、管理员处理反馈、越权请求被拒绝。
4. 如果受环境限制无法验证，必须在交付报告中明确写出未验证项、原因和补救步骤，不得隐瞒。

### H9 注释必须符合统一标准

代码注释、文档字符串、配置注释的写法以仓库根目录 `SKILL.md` 为标准，并遵守本文件第六节的执行卡。注释不合规视为交付不合格。

### H10 交付必须完整、可接手

1. 交付物不是若干代码片段，而是可直接安装、初始化、启动、测试的完整项目文件夹。
2. README 必须让没有参与开发的人从零启动。
3. 必须提供 `.env.example`，并逐项说明必填项。
4. 必须提供数据库迁移和初始化管理员的方法。
5. 必须提供健康检查方法和常见故障处理。
6. 不得留下“TODO 后续补”“临时这样写”“这里先不实现”等未完成状态作为最终交付。

## 四、独立运行与配置隔离

### 4.1 环境变量

1. 项目根 `.env` 是后端与基础设施的唯一真实配置入口；`.env.example` 提供完整模板。
2. 后端从项目根读取 `.env`，不得假设启动时当前目录一定是 `backend/`。建议用配置文件位置推导项目根：

```python
PROJECT_ROOT = Path(__file__).resolve().parents[3]
```

3. 前端只允许在 `frontend/.env.example` 中放 Vite 公共变量，例如 `VITE_API_BASE_URL`、`VITE_APP_MODE`；不得放密钥。
4. `.env.example` 中每个变量都要有中文说明；配置值使用占位符，不得填入真实密钥或本机绝对路径。
5. 如果某个配置文件会被工具以本地编码读取并要求纯 ASCII，只删除英文注释，不写入中文，避免解析失败。

### 4.2 依赖隔离

1. 后端依赖写入 `backend/requirements.txt`，版本约束要明确；安装后的虚拟环境位于 `backend/.venv/`。
2. 前端依赖写入 `frontend/package.json`，并提交 `package-lock.json`；`npm ci` 必须可复现安装。
3. 不得依赖仓库根目录的 `.venv`、`node_modules`、`.uv-cache`、`.hf-cache`。
4. 模型缓存默认放在项目内 `.hf-cache/`，通过 `RAG_EMBEDDING__CACHE_DIR` 覆盖；首次下载慢要在 README 中说明。
5. 不得把依赖安装到全局 Python 环境或全局 npm 目录作为项目运行前提。

### 4.3 全局配置与路径

1. 所有路径默认值必须相对项目根推导，或来自环境变量。
2. 禁止硬编码 `C:\Users\...`、桌面路径、父目录路径、旧项目目录名。
3. `RAG_RESOURCE_DIR` 默认指向本项目 `resource/`。
4. 上传目录、索引目录、日志目录、模型缓存目录全部位于本项目内。
5. 配置中不得出现 `product`、`demo`、`agent` 作为运行依赖；品牌文案可以改为“校园 RAG 知识库系统”。

### 4.4 端口与数据库默认值

为避免与现有三版冲突，默认使用：

| 项目 | 默认值 | 说明 |
| --- | --- | --- |
| 后端端口 | `8004` | 现有三版为 8001、8002、8003 |
| 管理端端口 | `5174` | 现有三版为 5171、5172、5173 |
| 用户端端口 | `5175` | 与现有三版错开 |
| 数据库名 | `rag_campus` | 禁止复用 `rag_product`、`rag_agent`、`rag_system` |
| Redis 库号 | `4` | 避免与现有项目共用同一个库 |
| MySQL 容器端口 | `3308` | 如使用项目内 compose；复用现有 MySQL 时只要求独立库名 |
| Redis 容器端口 | `6380` | 如使用项目内 compose；也可连接现有 Redis 的独立库号 |

所有值必须可通过 `.env` 覆盖。README 中写清楚默认值，避免用户误连旧库。

### 4.5 启动与健康检查

1. 提供项目内一键初始化脚本，至少完成：创建虚拟环境提示、安装依赖、复制 `.env.example`、执行数据库迁移、初始化管理员。
2. 提供项目内启动脚本，能分别启动后端、管理端、用户端，或通过参数选择。
3. 提供健康检查脚本或命令，检查后端 `/health`、数据库连接和前端可访问性。
4. 脚本内的路径必须相对脚本位置或项目根计算，不得写死本机路径。
5. 如果提供 `docker-compose.yml`，项目名、容器名、卷路径、端口必须独立，所有卷使用 `./data`、`./storage` 等相对路径。

### 4.6 独立运行验收

## 五、构建实施规则

### 5.1 构建来源与实现边界

1. 本项目从零构建，不复制 `product/backend` 与 `product/frontend` 的代码；`product/` 只用于对照业务流程、页面结构与接口行为。
2. 检索与生成必须基于 LangChain 组件实现，不得绕开 LangChain 自己拼装召回、融合与精排，也不得另外引入一套未声明的检索框架。
3. 初始检索参数沿用三版已验证的默认值：向量 Top-50、BM25 Top-50、RRF k 为 60、精排取前 5 条、上下文预算 6000 字。参数通过环境变量暴露，不得散落在业务代码中。

5. 生成链路使用 LCEL 组合：提示模板、聊天模型、输出解析；流式输出通过 `astream` 实现，引用编号由检索结果顺序确定。

1. 本阶段实现本地账号密码认证，认证层统一为会话签发与会话校验；阶段三接入企业微信网页授权，不预留其他身份源。

### 5.6 前后端双模式要求

1. 管理端保留现有完整页面：问答、知识库、检索策略、模型设置、日志、反馈处理、用户与权限。
2. 用户端只保留：登录、问答、反馈、个人菜单。
3. 用户端不得加载管理页面代码，不得展示管理菜单，不得暴露管理接口地址和参数结构。
4. 管理端与用户端共享同一后端、同一用户表、同一知识库、同一反馈表。
5. 管理端和用户端可以使用同一视觉语言，但管理端必须保留完整侧边栏，用户端保持单列问答体验。
6. 最低适配 1366×768；本阶段不做移动端 H5。

### 5.7 反馈闭环要求

1. 反馈快照由后端按消息 ID 读取并保存，不信任客户端提交的问题、答案和引用文本。
2. 反馈表至少包含：工单号、提交人、会话与消息 ID、知识库、策略、问题快照、答案快照、引用快照、类型、描述、期望答案、联系方式、状态、处理人、内部备注、用户可见回复、驳回原因、时间字段。
3. 状态流转只允许：待处理到处理中、待处理到已解决、待处理到已驳回、处理中到已解决、处理中到已驳回；驳回必须填写原因。
4. 所有状态变更记录操作人、时间、前后状态和备注。
5. 用户只能查看自己的反馈；管理员只能通过管理端接口查看全部反馈。
6. 反馈提交必须登录、限频、校验长度、做 XSS 转义；附件如实现，必须校验类型、大小并存储在非公开目录。

## 六、代码注释规范执行卡

### 6.1 标准来源

1. 代码注释、文档字符串、配置注释的唯一标准是仓库根目录 `SKILL.md`（即 `skill.md`，`comment-cleanup`）。
2. 开始编码前先读 `SKILL.md`；本节的规则是执行摘要，若与 `SKILL.md` 冲突，以 `SKILL.md` 为准。
3. 如果项目被单独复制到仓库外，`SKILL.md` 可能不可用；此时仍按本节规则执行，并建议把标准副本放入项目 `docs/` 后再交付。
4. 本节适用于 Python、JavaScript、TypeScript、Vue、CSS，以及 ini、yml、toml、conf、sh、Dockerfile、`.env` 等配置文件的注释。
5. `SKILL.md` 要求使用 `scan_comments.py` 扫描。当前仓库若找不到该脚本，先在项目和仓库内查找；找不到就按规则逐文件人工检查，并在报告中说明“扫描脚本缺失，已人工检查”，不得谎称已运行扫描。

### 6.2 硬性规则

1. 注释语言统一为中文。英文说明翻译为中文；技术专有名词、模型名、API 名、版本号可保留原文。
2. 注释只允许出现中文、数字、英文字母、常用标点与括号。
3. 禁止在注释文本中出现：等号、箭头、星号、井号、竖线、反引号、波浪号、制表符画线等符号。包括 `=`、`->`、`→`、`←`、`★`、`===`、`---`、`|`、`*`、`` ` ``、`~`、`**`。
4. 连字符只保留在专有名词和版本号内，例如 `bge-reranker-v2-m3`；不用于表达“到”或“变成”。
5. 范围统一写成“5 到 10”，不写 `5~10`。百分号、加号、小数点在数值表达中可保留。
6. 代码标识符避免用下划线形式书写，改写成中文，例如 `chunk_id` 写成“分块 ID”。
7. 注释只解释紧邻代码的当前行为与原因。与当前行无关的背景、跨文件约定、模块历史一律删除；确需跨文件说明时，只保留一句必要约束。
8. 禁止提示词式、过程式、来源式内容。只写代码现在是什么，不写谁要求的、改了什么、修了什么、以后做什么。
9. 段落分隔线、横幅注释、文件头装饰，能删就删；需要保留标题时写成单个中文短语。
10. 注释必须与代码当前行为一致。代码改了，注释同步改；不能留过期说明。

### 6.3 禁止写法与正确写法

| 禁止 | 正确 |
| --- | --- |
| 按照要求，背景改为白色 | 白色背景 |
| 根据用户反馈，回答结束后不自动滚动 | 回答结束后不自动滚动到底部 |
| 修复日志文件被占用的问题 | 清空日志前先释放文件句柄 |
| 本次新增本地模型热切换 | 支持运行中切换在线模型与本地模型 |
| 为了满足需求文档第 3 条，第 3 轮作答 | 第 3 轮强制输出最终答案 |
| TODO 后续支持多图 | 当前仅支持单图上传，或删除 |
| 与 product 版本保持一致，不要单独改 | 删除 |
| 这里临时这样写，以后重构 | 删除 |
| 注意：原来这里会崩溃 | 删除，或在确有约束时写“空值需先过滤” |

判断标准：把注释读给一个只看到这个文件的人，他能否据此理解这一行代码。不能，就删或重写。

### 6.4 必须保留的指令类注释

以下属于工具指令，不是说明文字，保持原样：

- `#!/usr/bin/env python`
- `# -*- coding: utf-8 -*-`
- `# noqa`、`# type: ignore`、`# pragma: no cover`
- `# fmt: off`、`# isort: skip`、`# pylint: disable`、`# mypy: ...`
- `// eslint-disable-next-line`、`// prettier-ignore`、`/* eslint-disable */`
- `/* @ts-ignore */`

JSDoc 的 `@param`、`@returns` 标签保留，标签后的说明文字必须改成中文。

### 6.5 执行流程

1. 扫描：优先运行 `scan_comments.py`，得到违规清单与统计。
2. 分批：按目录分批处理，逐文件先读全文，再改注释。
3. 改写：只替换注释文本，不动代码行、UI 文案、日志文案、Prompt 常量、配置值。
4. 复核：再次扫描，确认违规为 0 或只剩指令类注释；Python 执行语法编译检查，前端执行构建或静态检查。
5. 汇报：给出修改文件数、清理条目数、仍保留的指令类注释类型。

### 6.6 例外与边界

1. 第三方依赖、构建产物、压缩文件、自动生成文件不纳入注释清理范围，也不要手改。
2. 配置文件中若工具要求纯 ASCII，只删除英文注释，不写入中文。
3. 注释清理不得改变业务逻辑、字符串、配置值或提示词内容。
4. 新增代码的注释必须一次写合规；迁移代码在触碰到的文件内清理违规注释，交付前对全项目做一次检查。
5. 不得为了“注释好看”批量重写整个文件，导致 diff 无法审查。

### 6.7 完成标准

- 注释中不再出现被禁止的符号。
- 注释语言统一为中文，专有名词除外。
- 不存在“按要求、本次、修复了、以后、临时”等过程性内容。
- 注释与紧邻代码行为一致，删掉后不损失关键信息。
- 代码可正常编译或构建。

## 十、协作与阻塞处理

### 10.1 开始前确认

除非用户另有明确指令，按以下默认值执行，不必逐项追问：

- 迁移来源：`product/`。
- 当前阶段范围：用户明确指定的阶段文档；未指定时为《阶段一.md》。
- 认证方式：本地账号密码；阶段三追加企业微信网页授权。
- 数据库：独立库 `rag_campus`。
- 端口：后端 8004，管理端 5174，用户端 5175。
- 示例语料：可创建，但必须标注“示例文档，非正式制度”。

遇到以下情况必须提问：

1. 用户要求与《阶段一.md》权限矩阵冲突。
2. 需要复用 `product/` 的历史数据，但未说明迁移范围。
3. 需要接入企业微信，但未提供应用凭证、回调地址、测试账号和同名站内账号。
4. 需要修改仓库根目录共享文件。
5. 需要执行不可逆操作。
6. 环境缺少 MySQL、Node、Python 等必要组件，且无法在项目内解决。

### 10.2 里程碑汇报

每完成一个里程碑，简短汇报：

- 完成了什么。
- 改了哪些目录或文件。
- 执行了哪些验证，结果如何。
- 下一步是什么。
- 是否有阻塞。

不要用大段计划代替实际进展，也不要在未验证时宣称完成。

### 10.3 上下文恢复

上下文被压缩或会话恢复后，先读：

1. 本文件。
2. 《阶段一.md》中当前里程碑相关章节。
3. 项目 `README.md` 和当前代码状态。
4. `git status`，确认没有覆盖用户未提交的改动。

确认当前进度后再继续，不得凭记忆假设文件已经改好。

### 10.4 用户授权 subagent 的处理

即使用户授权，也必须：

1. 记录授权原话和范围。
2. 只把边界清晰、可独立验证的子任务交给子智能体。
3. 不让子智能体修改本项目核心配置、数据库迁移、权限逻辑等高风险部分，除非用户明确要求。
4. 主智能体逐项复核子智能体产出，自己运行验证。
5. 在交付报告中说明使用了子智能体、承担了什么任务、如何复核。

默认状态始终是：不使用 subagent。
