## 一、阶段目标

一句话概括：

> 让每一条答案都只来自「当前有效、用户有权查看、能够回溯到具体条款」的文档，并用真实校园问题集证明系统没有因为治理改造而变差。

本阶段必须达成以下结果：

1. **权限真实生效**：学生只能检索公开文档；教职工能检索公开文档和本部门内部文档；管理员能管理全部文档。无权限文档不得进入候选池，不得出现在引用中。
2. **版本唯一有效**：同一制度只召回当前有效版本；旧版本废止后不再被检索；未来生效版本在生效日前不参与问答。
3. **文档生命周期完整**：支持草稿、发布、废止、归档；支持版本号、生效日期、责任部门、责任人、复核日期；支持单文档增量重建。
4. **解析质量可用**：表格转为可检索结构，制度文本按章、节、条切分，父子块能同时保留条款上下文与细粒度命中。
5. **引用可核验**：引用展示文件名、页码、条款号、版本号、生效日期和责任部门；答案页有统一免责声明。
6. **质量可量化**：建立 300 到 500 条校园黄金测试集，复用 demo 的 Recall、MRR、nDCG、忠实度与答案相关性指标，形成基线并支持回归。
7. **答不了能转办**：无依据、引用缺失、制度过期、用户主动求助时，可转人工或转责任部门，形成可追踪工单。
8. **阶段一不回归**：登录、双前端、权限、问答、反馈、审计等阶段一能力保持可用。

## 三、总体方案

### 3.1 核心原则

1. **权限前置**：权限过滤必须发生在向量召回与 BM25 召回内部，不能先召回再裁剪。融合、精排、上下文拼接都只能看到有权文档。
2. **当前版本唯一**：检索条件必须包含「已发布、已生效、未废止」；同一逻辑文档最多一个当前版本。
3. **先建后切**：新版本先完成解析、索引、一致性校验，再切换当前版本；失败时旧版本继续服务，不能出现检索真空。
4. **结构优先**：制度文档优先按章、节、条切分；表格独立成块；父子块保证命中细粒度内容时仍能带回条款上下文。
5. **引用可核验**：引用不是装饰，必须能回到「文件、页码、条款、版本、生效日期」。
6. **评估可回归**：任何治理改造都要用同一套黄金测试集对比基线；安全与时效指标是硬门槛。
7. **先治理一个部门**：本阶段只接入教务处，跑通「文档治理、权限、版本、评估、转办」闭环，再复制到其他部门。

### 3.2 目标架构

```text
用户请求
   ↓
认证与角色解析（阶段一）
   ↓
检索范围构造 RetrievalScope
   user_id / role / department_id / now
   ↓
权限与时效过滤（两路召回内部前置）
   向量召回：Chroma metadata where
   BM25 召回：全量打分后按权限掩码，再取 Top-k
   ↓
RRF 融合 → 候选池 → 精排 → Top-k
   ↓
父块回填与上下文拼接
   子块命中，补回所属条款/章节
   ↓
生成答案 + 引用解析
   引用附文件、页码、条款、版本、生效日期、责任部门
   ↓
答案页免责声明 + 反馈/转人工入口
```

入库链路：

```text
上传文档
   ↓
解析正文与表格
   ↓
条款识别与父子块构建
   ↓
写入文档主表与版本表（草稿）
   ↓
解析、分块、向量索引、BM25 索引（版本级）
   ↓
一致性校验与抽样检索
   ↓
发布：切换当前版本，旧版本废止
   ↓
检索只读取当前有效版本
```

## 四、角色、部门与文档权限

### 4.1 角色扩展

阶段一只有 `admin` 与 `user` 两级。本阶段扩展为四级：

| 角色 | 标识 | 说明 | 可见文档 |
| --- | --- | --- | --- |
| 系统管理员 | `admin` | 管理全部部门、用户、知识库、文档、配置、日志、评估 | 全部 |
| 部门管理员 | `dept_admin` | 管理本部门知识库、文档、版本、反馈转办；不能管理其他部门 | 公开 + 本部门 |
| 教职工 | `staff` | 问答、反馈、查看公开与本部门内部文档 | 公开 + 本部门 |
| 学生 | `student` | 问答、反馈、查看公开文档 | 公开 |

> 说明：《项目落地方案.md》提出 `student`、`staff`、`admin` 三级角色。本阶段增加 `dept_admin`，作为 `admin` 在部门范围内的受限子集，用于部门自治；它不改变 `admin` 的全局权限，也不替代 `staff` 的问答权限。

迁移要求：

1. 阶段一 `user` 角色迁移为 `student`；`admin` 保持不变。
2. 新增 `staff`、`dept_admin`；由管理员创建或批量导入，不开放自助注册。
3. 用户表增加 `department_id`，阶段一的 `department` 字符串迁移为部门主数据；无法匹配的历史值进入「待分配」部门，不得默认开放内部文档。
4. 角色变更后，下一次请求生效；已签发凭证不需要重新登录，但后端每次请求重新解析角色与部门。
5. `dept_admin` 不得把自己提升为 `admin`；不得管理其他部门；不得移除最后一个 `admin`。
6. 阶段一权限矩阵继续有效，新增角色在管理端的可见范围按本阶段矩阵执行。

### 4.2 文档可见性

文档新增三个可见性级别：

| 可见性 | 标识 | 可见对象 | 说明 |
| --- | --- | --- | --- |
| 公开 | `public` | 全部登录用户 | 全校应知应会的制度、办事指南 |
| 部门内部 | `department` | 本部门 `staff`、`dept_admin`、`admin` | 仅本部门教职工可见，学生不可见 |
| 仅管理员 | `admin_only` | `admin` | 敏感材料、草稿、审计材料；本阶段不进入问答索引 |

文档必须同时具备：

- `department_id`：归属部门，公开文档可为空或挂「全校」。
- `visibility`：三级可见性之一。
- `owner_user_id`：责任人，负责内容复核与到期处理。
- `review_due_date`：下次复核日期，可为空但建议填写。

默认规则：

1. 上传文档默认 `department`，归属部门取上传时选择的部门；系统管理员未选择部门时进入「待分配」，在明确归属前不得发布。
2. 缺省不开放；没有明确可见性的文档不得发布。
3. `admin_only` 文档本阶段只允许管理端预览与下载，不写入问答索引；阶段三接入本地模型后再评估是否开放。
4. 公开文档可以由部门管理员发布，但必须经部门责任人确认；全局管理员可代发。

| 功能/资源 | admin | dept_admin | staff | student |

| 问答检索公开文档 | 允许 | 允许 | 允许 | 允许 |
| 问答检索本部门内部文档 | 允许 | 允许 | 允许 | 禁止 |

### 4.4 权限判定

后端每次问答请求构造检索范围，不允许从请求体接收角色或部门：

```text
RetrievalScope
  user_id
  role
  department_id
  now
  allow_public = true
  allow_department = role in (staff, dept_admin, admin)
```

检索条件：

```text
lifecycle_status = published
AND effective_date <= now
AND (repealed_at IS NULL OR repealed_at > now)
AND (
      visibility = public
   OR (visibility = department AND department_id = scope.department_id AND scope.allow_department)
)
```

补充要求：

1. 阶段二 `admin_only` 不进入问答索引，因此检索条件只包含 `public` 与 `department`；阶段三如开放，再增加 `admin_only` 分支。
2. 管理员在管理端预览草稿或历史版本时，使用独立管理接口，不复用问答检索接口。
3. 公开文档也必须要求登录；未登录返回 401。
4. 用户的部门来自用户表，不信任前端传入的 `department_id`。
5. 超级管理员不因「全部可见」而跳过版本与时效过滤；过期文档对管理员也不应在正常问答中返回，管理端通过版本历史查看。

### 4.5 检索层过滤

#### 4.5.1 向量召回

1. 在 Chroma 查询时构造 metadata `where` 条件，包含 `lifecycle_status`、`effective_date`、`repealed_at`、`visibility`、`department_id`。
2. 条件必须覆盖「公开」「本部门内部」两类允许范围；不允许只按知识库过滤。
3. Chroma 集合仍按知识库隔离；metadata 过滤是第二道边界。
4. 过滤条件由统一的 `build_acl_filter(scope)` 生成，禁止在各检索器里各写一套。
5. 需要为 Chroma 过滤字段建立固定 metadata 类型：日期统一 ISO 字符串，部门用整数，可见性用短字符串。

#### 4.5.2 BM25 召回

1. BM25 索引的每条文档块必须携带与向量索引一致的 ACL metadata。
2. 查询时先对全部语料打分，再用权限与时效掩码把无权或过期文档分数置零，最后取 Top-k。
3. 禁止先取 Top-50 再在 Python 里过滤；否则有权文档可能被无权文档挤出候选池。
4. 掩码计算使用 NumPy 向量化，不得逐条 Python 循环；在 10 万块规模下记录过滤耗时。
5. 若 BM25 索引文件尚未包含 ACL 字段，必须重建该知识库的 BM25 索引，不得用「先查后过滤」过渡。

#### 4.5.3 融合与生成

1. RRF 融合只接收已过滤结果；融合层不得再次引入未过滤候选。
2. 精排只对融合后的有权候选打分。
3. 上下文拼接只使用有权候选；引用列表不得出现无权文档。
4. 检索日志记录 `role`、`department_id`、`visibility_scope`、`document_version`，不记录用户敏感信息。

#### 4.5.4 权限变更后的索引

1. 文档可见性、归属部门变化时，必须更新该文档全部块的 metadata；底层不支持批量更新时，重建该文档版本索引。
2. 用户部门变化不需要重建索引，下一次请求按新部门过滤。
3. 文档废止或归档时，必须把 `lifecycle_status` 更新为不可检索，或从索引删除；两者择一，但必须保证检索层过滤生效。
4. 任何 ACL 变更都写入审计日志，记录操作人、时间、文档、变更前后值。

### 4.6 文档预览与下载

1. 引用点击默认只展示「文件名、页码、条款、命中片段」，不直接返回完整文档。
2. 完整预览/下载按 ACL 判定：`admin` 全部；`dept_admin` 与 `staff` 可预览公开文档及本部门文档；`student` 仅公开文档。
3. 预览接口必须校验文档 ID 与当前用户范围，不能只凭文档 ID 返回文件。
4. 越权预览返回 404，避免通过错误码判断文档是否存在。
5. 预览行为写入审计日志，记录用户、文档、时间；不记录正文。

### 4.7 审计

新增或扩展以下审计事件：

- 文档创建、上传、解析、发布、废止、归档、版本切换。
- 文档可见性、归属部门、责任人变更。
- 知识库创建、编辑、启停、删除。
- 评估任务启动、报告导出。
- 反馈转办、受理、回复、办结。
- 越权访问尝试（401/403/404）。

审计字段至少包含：操作人、角色、部门、动作、目标类型、目标 ID、变更摘要、IP、时间。变更摘要脱敏，不记录完整正文、密钥、令牌。

## 五、文档生命周期

### 5.1 两类状态必须分开

阶段一及现有 product 只有处理状态 `pending / parsing / indexing / completed / failed`。本阶段新增业务生命周期状态，二者不得混用：

| 状态类型 | 字段 | 取值 | 用途 |
| --- | --- | --- | --- |
| 处理状态 | `process_status` | pending / parsing / indexing / completed / failed | 描述解析入库进度 |
| 生命周期状态 | `lifecycle_status` | draft / published / repealed / archived | 描述制度是否可被检索 |

要求：

1. 只有 `process_status = completed` 且 `lifecycle_status = published` 且已生效的版本才能进入检索。
2. 处理失败不得自动发布；解析失败必须保留错误信息并允许重试。
3. 废止不等于删除；废止文档保留版本历史与原文，供审计与追溯。
4. 归档用于长期保存，不参与问答；归档后不得再发布，除非管理员显式恢复。

### 5.2 数据模型

推荐采用「文档主表 + 版本表」：

- `documents`：逻辑文档，保存标题、文号、知识库、归属部门、可见性、责任人、当前版本、复核日期。
- `document_versions`：具体版本，保存版本号、文件路径、文件哈希、生效日期、废止日期、生命周期状态、处理状态、分块数、发布人、发布时间。

约束：

1. 同一逻辑文档最多一个 `lifecycle_status = published` 且 `repealed_at IS NULL` 的版本。
2. 同一逻辑文档的版本号唯一；版本号建议使用 `2025`、`2025-修订`、`v2` 等可读形式，具体规则由部门确认。
3. `current_version_id` 指向当前发布版本；切换必须原子更新。
4. 旧版本废止时写入 `repealed_at`，并记录 `superseded_by_version_id`。
5. 新版本可以设置未来生效日期；在生效日前 `effective_date > now`，检索不返回。
6. 文件哈希用于识别重复上传与内容变更；同一文件重复上传时提示已存在，不静默覆盖。

### 5.3 发布流程

```text
上传文件
  → 创建文档主表与版本记录（draft）
  → 解析、分块、写入版本级索引（staging）
  → 一致性校验：分块数、向量数、BM25 数、抽样检索
  → 部门责任人复核
  → 发布：数据库事务切换 current_version
  → 旧版本置为 repealed，并从检索索引移除或标记不可检索
  → 审计与通知（站内）
```

要求：

1. **先建后切**：新版本索引未通过校验前，不得改动旧版本。
2. 发布失败时，新版本回到草稿或失败状态，旧版本继续服务。
3. 发布过程中禁止出现「两个当前版本」；数据库唯一约束与事务必须保证。
4. 旧版本废止后，正常问答不再返回旧版本；管理端版本历史仍可查看与预览。
5. 如果新版本索引切换成功但旧版本清理失败，进入补偿队列并告警；检索以数据库 `current_version_id` 与索引 metadata 双重过滤为准。
6. 发布、废止、回滚都必须写审计日志。

### 5.4 单文档增量重建

1. 只对目标文档版本重新解析、分块、向量化；不得触发全知识库重嵌入。
2. 向量索引按 `version_id` 删除旧块、写入新块；Chroma 支持按 metadata 删除时优先使用。
3. BM25 索引是知识库级文件，允许从全部分块重建，但不得重新调用嵌入模型；重建耗时必须记录。
4. 重建完成后执行一致性校验：分块文件块数、向量条数、BM25 条数必须一致。
5. 分块策略变化才允许全知识库重建；普通内容更新、版本发布、ACL 变更不得全量重建。
6. 重建失败保留旧索引与旧版本，不得先删后建。

### 5.5 索引 metadata

向量与 BM25 的每个块必须至少包含：

| 字段 | 说明 |
| --- | --- |
| `chunk_id` | 稳定块编号 |
| `document_id` | 逻辑文档 ID |
| `version_id` | 版本 ID |
| `source` | 文件名 |
| `page` | 起始页码 |
| `page_end` | 结束页码，可为空 |
| `department_id` | 归属部门 |
| `visibility` | public / department / admin_only |
| `lifecycle_status` | published / repealed 等 |
| `effective_date` | 生效日期，ISO 字符串 |
| `repealed_at` | 废止时间，ISO 字符串或空 |
| `doc_no` | 文号 |
| `doc_title` | 文档标题 |
| `version_label` | 版本号 |
| `chunk_type` | text / clause / table / heading |
| `article_no` | 条款号，可为空 |
| `parent_chunk_id` | 父块 ID，可为空 |

要求：

1. metadata 值必须是 Chroma 支持的简单类型，不写嵌套 JSON。
2. 日期统一使用 `YYYY-MM-DD` 或 ISO 8601 字符串，避免本地化格式导致过滤错误。
3. 修改 metadata 字段后，必须同步更新向量与 BM25 两侧。
4. 索引重建后核对 metadata 完整性，缺失 ACL 字段的块不得进入检索。

### 5.6 一致性、回滚与责任

1. 每次发布或重建后执行索引一致性检查：块数、向量数、BM25 数、当前版本号。
2. 健康检查增加「索引版本与数据库当前版本是否一致」检查；不一致时返回 degraded，并阻止新版本切换。
3. 保留上一版本索引直到新版本稳定运行；建议保留至少一个旧版本，便于快速回滚。
4. 回滚操作必须显式、可审计；回滚后旧版本恢复为 published，新版本置为 repealed 或 draft。
5. 每个知识库指定责任部门与责任人；文档设置复核日期，阶段三接入到期提醒。
6. 文档发布、废止、回滚、权限变更的操作人和原因必须可追溯。
7. 《项目落地方案.md》要求旧版本从索引移除；本阶段允许保留上一版本索引用于回滚，但必须通过 metadata 过滤保证旧版本不可检索，稳定后按保留策略清理。

## 六、结构化解析与分块

### 6.1 表格解析

1. PDF 使用 `pdfplumber` 提取表格；保留页码、表格序号、表头。
2. DOCX 使用 `python-docx` 读取表格；按文档正文顺序与段落合并，避免表格位置错乱。
3. 表格统一转为 Markdown 表格文本；保留表头、单位、注释。
4. 表格块不得被普通递归分块切断；超过长度上限时按行拆分，并在每段重复表头。
5. 表格 metadata 标记 `chunk_type = table`、`table_id`、`row_start`、`row_end`。
6. 表格内容必须与正文一样进入向量与 BM25 索引；BM25 分词对表头与单元格分别处理。
7. 表格解析失败时保留原始文本并记录警告，不得静默丢弃整张表。

### 6.2 条款级切分

1. 制度类文档优先识别以下结构：
   - `第X章`、`第X节`、`第X条`。
   - `一、`、`（一）`、`1.`、`（1）` 等条目。
   - 文号、发布日期、生效日期、废止说明。
2. 条款切分以「条」为主要检索单元；章、节作为父级上下文。
3. 条款正文过长时，在条内按段落或句号二次切分，但保留 `article_no` 与父块 ID。
4. 条文中的表格独立成表块，挂到所属条款下。
5. 无法识别结构的文档回退到 recursive 或 fixed 策略，不得强行按错误条款切分。
6. 条款号必须在文档内唯一；重复条款号进入质量告警，人工确认后再发布。

### 6.3 父子块

1. 子块用于召回：段落、句子、表格行组等细粒度内容。
2. 父块用于上下文：章标题、节标题、条款全文、表格标题与表头。
3. 子块 metadata 保存 `parent_chunk_id`；父块保存在分块文件或数据库中，不强制进入向量索引。
4. 检索命中子块后，按父块 ID 回填父级上下文，再拼入生成上下文。
5. 父块回填必须受上下文预算限制；超长条款只回填标题、条款号与命中段落前后各一段。
6. 引用仍指向子块页码与条款号；不得因为回填父块而把引用页码改成章节起始页。
7. 父子块去重：同一父块下多个子块命中时，合并上下文，避免重复。

### 6.4 分块策略

知识库新增 `chunk_strategy` 可选值：

| 策略 | 适用场景 | 说明 |
| --- | --- | --- |
| `clause` | 制度、办法、规定 | 条款级切分 + 父子块，默认推荐 |
| `recursive` | 一般说明文档 | 现有递归语义切分 |
| `fixed` | 格式混乱或对照实验 | 固定窗口，保留兼容 |

要求：

1. 教务处制度库默认 `clause`；无法识别条款时自动回退 `recursive`，并在入库报告中说明。
2. 策略变更需要重建该知识库全部索引；普通文档更新不需要切换策略。
3. 分块参数（长度、重叠、最小块）走配置，不写死在代码。
4. 分块结果保存策略名与参数，便于复现与评估。

### 6.5 分块元数据

除第五节索引 metadata 外，分块文件/数据库还需保存：

- `chunk_index`：文档内顺序。
- `text`：块正文。
- `parent_text`：父块上下文，可为空。
- `chapter`、`section`、`article_no`。
- `table_id`、`row_start`、`row_end`。
- `token_count` 或字符数。
- `content_hash`：块内容哈希，用于去重与增量判断。

### 6.6 质量检查

入库完成前必须检查：

1. 空块、纯空白块、纯页眉页脚块不得进入索引。
2. 单块长度不超过配置上限；超长块必须二次切分。
3. 表格块必须包含表头，且不得把一行拆到两个块。
4. 条款块必须有条款号；无条款号时标记为普通文本块，不得伪造条款号。
5. 页码必须可回溯；无法确定页码的块标记 `page = unknown`，引用时明确提示。
6. 同一文档内 `content_hash` 重复块去重，避免重复召回。
7. 入库报告列出文件数、块数、表格数、条款数、失败文件与警告。

## 七、引用、版本与答案可信

### 7.1 引用字段

引用对象至少包含：

```text
index
chunk_id
source
page
page_end
article_no
doc_no
doc_title
version_label
effective_date
department
label
text
```

要求：

1. `label` 示例：「[1]《XX 管理办法》（2025 修订）第三十八条，第 12 页」。
2. 没有条款号时显示文件名与页码；没有页码时显示文件名与条款号。
3. 引用列表按答案中首次出现顺序编号，保持与生成上下文一致。
4. 越界引用编号必须检测并记录；答案页可提示「引用编号异常」，后台进入质量告警。
5. 引用只来自当前请求有权访问的文档；不得通过引用泄露无权文档的标题、文号或片段。

### 7.2 答案页展示

1. 答案下方固定展示免责声明：「本回答由系统根据知识库自动生成，仅供参考，具体以正式文件为准。」
2. 每条引用展示文件名、页码、条款号、版本号、生效日期、责任部门。
3. 引用卡片可展开查看命中片段；完整原文预览按 ACL 控制。
4. 答案使用的策略、知识库、检索耗时可在「检索详情」中查看；用户只能看自己的回答。
5. 答案涉及废止版本时，不得引用旧版本作答；如果用户明确询问旧版本，回答应说明当前有效版本，并提示旧版本已废止。

### 7.3 无依据与拒答

1. 检索结果为空、全部低于阈值、或生成答案无有效引用时，系统应明确回答「根据现有知识库无法确定」，不得编造。
2. 拒答时展示可选的「转人工/转部门」入口，并保留问题、检索范围与命中情况。
3. 生成答案中的引用必须来自本次上下文；无引用答案不得标记为「已核实」。
4. 引用越界、引用缺失、引用与答案不一致进入质量日志，供评估与反馈处理。
5. 对高敏感问题（如处分、学籍、资助金额）建议强制转人工，具体清单由教务处确认。

### 7.4 版本冲突

1. 同一逻辑文档只允许一个当前有效版本进入索引。
2. 新旧版本交替期间，检索以数据库 `current_version_id` 为准；旧版本即使索引尚未清理，也必须被 metadata 过滤。
3. 评估集增加「新旧版本同时存在」用例，验收标准为旧版本召回次数为 0。
4. 管理员可以在版本历史中对比新旧版本差异；差异对比只做文本展示，不做自动判定。

## 八、黄金测试集与评估回归

### 8.1 测试集来源与规模

1. 规模：300 到 500 条，首期建议 400 条。
2. 来源：教务处真实咨询工单、常见问题、辅导员/教务员访谈、现有制度目录。
3. 类别与建议占比：

| 类别 | 建议占比 | 说明 |
| --- | --- | --- |
| 语义泛化 | 40% | 学生口语化提问，措辞与制度文本不一致 |
| 术语精确 | 25% | 条款号、文号、专有名词、精确匹配 |
| 多跳推理 | 20% | 跨条款、跨文件、需要组合依据 |
| 时效与版本 | 10% | 新旧版本、生效日期、废止文档 |
| 权限与拒答 | 5% | 越权、无依据、应转人工 |

4. 每条样本必须标注所属知识库、部门、相关块/页码、参考答案要点、期望行为。
5. 真实工单涉及个人信息时必须脱敏；姓名、学号、手机号、身份证号不得进入测试集。
6. 测试集需要版本号与审核人；每次修改记录变更原因，不能随意改标注。

### 8.2 样本格式

建议使用 JSONL，每行一条：

```json
{
  "id": "JWC-0001",
  "question": "转专业后之前修过的课还算不算？",
  "category": "语义泛化",
  "department": "教务处",
  "kb_id": 1,
  "relevant_chunk_ids": ["clause:...:p12:c3:ab12cd34"],
  "relevant_pages": [{"source": "学籍管理规定.pdf", "page": 12}],
  "reference_answer": "已修课程符合认定条件的，可申请学分认定，具体见第三十八条。",
  "expected_behavior": "answer",
  "expected_sources": ["学籍管理规定.pdf"],
  "forbidden_sources": [],
  "version": "2025",
  "note": "多跳：转专业 + 学分认定",
  "annotator": "教务老师A",
  "reviewed_at": "2026-11-20"
}
```

`expected_behavior` 取值：

- `answer`：应给出带引用答案。
- `refuse`：应明确拒答，不得编造。
- `transfer`：应建议转人工/转部门。
- `forbidden`：不得召回或引用 `forbidden_sources` 中的文档。

### 8.3 指标

| 维度 | 指标 | 说明 |
| --- | --- | --- |
| 检索 | Recall@1/3/5/10、MRR、nDCG、Hit@k | 复用 demo 指标定义 |
| 生成 | 忠实度、答案相关性 | 复用 demo LLM 裁判，1 到 5 分 |
| 引用 | 引用正确率、引用召回率、越界引用率 | 引用是否正确对应依据 |
| 时效 | 废止文档召回次数、旧版本引用次数 | 必须为 0 |
| 权限 | 越权召回率、越权引用率 | 必须为 0 |
| 行为 | 拒答正确率、转人工正确率 | 对照 `expected_behavior` |
| 性能 | P50/P95 延迟、检索耗时、精排耗时 | 按目标部署环境记录 |
| 稳定性 | 评估失败率、接口错误率 | 评估任务可重试 |

### 8.4 复用 demo 评估模块

1. 复制 `demo/src/evaluation/metrics.py` 的 Recall、MRR、nDCG、Hit、Precision 实现，保持指标口径一致。
2. 复制 `judge.py` 的忠实度与答案相关性裁判逻辑；裁判 Prompt、温度、JSON 解析、失败重试策略保持一致。
3. 复制 `testset.py` 的校验、类别统计、页码级判定思路；扩展校园类别、版本、权限字段。
4. 复制 `retrieval_eval.py`、`generation_eval.py` 的分层抽样、逐题明细、汇总表结构。
5. 复制 `cli.py` 的命令行组织方式，改为本项目路径与配置；不得运行时导入 demo。
6. 评估模块放在 `backend/src/evaluation/`，测试使用 `backend/tests/evaluation/`。
7. 评估调用本项目检索服务与生成服务，不绕过 ACL；检索与生成质量可用专用 `admin` 或只读评估角色执行，权限类样本必须用对应 `student`、`staff`、`dept_admin` 测试账号执行；输出中不得泄露无权内容。

### 8.5 基线与回归门槛

1. 改造前先在当前迁移版本上跑一次基线，记录 Recall@k、MRR、nDCG、忠实度、答案相关性、引用正确率、P95。
2. 阶段二完成后使用同一测试集、同一分块策略、同一模型配置复跑。
3. 硬门槛：
   - 越权召回率 = 0。
   - 废止文档召回次数 = 0。
   - 旧版本引用次数 = 0。
   - 引用中的文档必须属于当前用户可访问范围。
4. 软门槛（建议值，评审确认）：
   - Recall@5 不低于基线 2 个百分点。
   - 引用正确率不低于 90%。
   - 忠实度平均分不低于 4.0（5 分制）。
   - 越界引用率不高于 1%。
   - 拒答正确率不低于 90%。
5. 如果指标下降超过门槛，必须先定位原因，不得直接上线；降级项必须经用户确认并记录。
6. 每次发布新版本制度、修改分块策略、修改检索参数、修改权限规则，都必须跑回归。

### 8.6 执行与报告

1. 提供 CLI：
   - `python -m src.evaluation.cli retrieval --testset data/evaluation/golden_v1.jsonl`
   - `python -m src.evaluation.cli generation --testset ... --limit 50`
   - `python -m src.evaluation.cli compare --baseline ... --current ...`
2. 管理端提供只读「评估报告」页：展示最近一次基线、当前结果、差异、失败样本；仅 `admin` 与 `dept_admin` 可看。
3. 报告保存为 Markdown + JSON；逐题明细保存 CSV；敏感测试集不提交仓库。
4. 评估任务耗时较长时使用后台任务；前端显示进度与失败原因。
5. 评估失败不得影响问答主流程；评估结果不得自动修改线上配置。

### 8.7 测试集数据治理

1. 真实测试集存放在受控目录，不提交公开仓库；仓库只保留脱敏样例与格式说明。
2. 测试集访问需要权限；导出与修改记录审计。
3. 个人信息最小化；无法脱敏的工单不进入测试集。
4. 测试集版本与知识库版本绑定；知识库大版本变更后重新标注受影响样本。

## 九、人工转接

### 9.1 触发条件

以下情况向用户展示「转人工/转部门」：

1. 检索无结果或全部低于阈值。
2. 生成答案无有效引用。
3. 系统明确拒答。
4. 用户点击「没解决」「转人工」。
5. 问题涉及高敏感事项，按部门配置强制转接。
6. 用户反馈类型为「知识库无相关内容」「制度过期」「回答不完整」。

### 9.2 流程

```text
用户点击转人工
  → 后端生成转办单，保存问题、答案快照、引用、知识库、策略、用户联系方式
  → 按知识库归属部门分配给 dept_admin
  → 管理端待办出现
  → 受理、回复、办结或退回补充
  → 用户「我的反馈」查看状态与回复
```

要求：

1. 转办单必须有唯一编号，格式建议 `TR-YYYYMMDD-0001`。
2. 快照由后端按消息 ID 读取，不信任客户端提交的答案文本。
3. 用户只能查看自己的转办单；部门管理员只能查看本部门；`admin` 查看全部。
4. 转办单状态沿用阶段一四态并新增 `replied`：待受理 `pending`、处理中 `processing`、已回复 `replied`、已办结 `resolved`、已退回 `rejected`。
5. 退回必须填写原因；回复必须填写用户可见内容；办结必须填写处理说明或回复。
6. 知识库未指定部门管理员或部门管理员停用时，转办单进入系统管理员待办；超过约定时限未受理则升级提醒。
7. 转办不直接修改知识库；知识库更新仍走文档发布流程。
8. 阶段二只做站内状态，不发送邮件/短信/企业微信通知；阶段三接入通知。

### 9.3 与现有反馈的关系

阶段一已有反馈表与反馈处理页。本阶段扩展现有反馈，不新建两套重复工单：

- 反馈新增 `kind`：`feedback`（普通反馈）/ `transfer`（转人工）。
- 新增 `assigned_department_id`、`assigned_user_id`、`transfer_reason`、`first_response_at`；办结时间沿用阶段一 `resolved_at`，不重复增加 `closed_at`。
- 转办单新增 `replied`（已回复）状态，与阶段一四态组合使用；不新增语义重叠的 `transferred` 状态。
- 状态流转：`pending` 到 `processing` 到 `replied` 到 `resolved`；`pending` 或 `processing` 可到 `rejected`；`replied` 可回到 `processing`，也可在用户确认或超时后到 `resolved`。
- 普通反馈 `kind = feedback` 不进入 `replied`，继续按阶段一四态流转；转办单 `kind = transfer` 使用完整五态。
- 管理端反馈页增加「转办」动作与部门筛选；用户端「我的反馈」展示转办状态。
- 阶段一的状态流转规则继续有效；新增状态必须有明确流转表与审计。

### 9.4 服务时限

建议值，由教务处确认：

- 首次响应：1 个工作日内。
- 一般问题办结：3 个工作日内。
- 复杂问题：可延期，但必须记录原因并通知用户。
- 超时未处理在管理端标红；阶段三接入提醒。

## 十四、验收标准

### 14.1 权限与 ACL

- [ ] 学生检索不到 `department` 与 `admin_only` 文档，引用列表不出现相关文件。
- [ ] 教职工能检索公开文档与本部门内部文档，检索不到其他部门内部文档。
- [ ] 部门管理员只能管理本部门文档与反馈，访问其他部门返回 403/404。
- [ ] 管理员可管理全部文档，但正常问答仍只返回当前有效、已发布文档。
- [ ] 未登录访问业务接口返回 401；普通用户访问管理接口返回 403。
- [ ] 直接构造文档 ID 预览他人文档返回 404，不泄露存在性。
- [ ] 向量召回与 BM25 召回都在过滤后取 Top-k；测试证明无权文档未进入候选池。
- [ ] ACL 变更后下一次检索立即生效，无缓存旧权限。
- [ ] 越权召回率 = 0，越权引用率 = 0。

### 14.2 生命周期与版本

- [ ] 同一逻辑文档最多一个当前发布版本，数据库约束生效。
- [ ] 新版本发布后，旧版本自动废止，正常问答不再召回旧版本。
- [ ] 未来生效版本在生效日前不被召回，生效日后自动可召回。
- [ ] 废止文档召回次数 = 0，旧版本引用次数 = 0。
- [ ] 发布失败时旧版本继续服务，不出现检索真空。
- [ ] 单文档重建不触发全知识库重嵌入；分块、向量、BM25 条数一致。
- [ ] 回滚可恢复到上一版本，回滚过程与结果有审计。
- [ ] 解析失败、索引失败有明确错误信息与重试入口。

### 14.3 结构化解析与分块

- [ ] PDF 与 DOCX 表格可被解析为结构化文本，表头保留。
- [ ] 长表格按行拆分时重复表头，不把一行拆成两块。
- [ ] 制度文档可识别章、节、条，条款号进入 metadata。
- [ ] 子块命中后能回填父级条款上下文，引用仍指向正确页码与条款。
- [ ] 无法识别条款的文档自动回退递归分块，不产生错误条款号。
- [ ] 空块、重复块、纯页眉页脚块不进入索引。
- [ ] 入库报告包含文件数、块数、表格数、条款数、失败与警告。

### 14.4 引用与答案

- [ ] 引用展示文件名、页码、条款号、版本号、生效日期、责任部门。
- [ ] 答案页固定展示免责声明。
- [ ] 无依据时明确拒答，不编造。
- [ ] 引用越界、引用缺失、引用与答案不一致被记录。
- [ ] 用户只能看到自己有权文档的引用与预览。
- [ ] 管理员可通过版本历史查看旧版本，但正常问答不使用旧版本。

### 14.5 黄金测试集与评估

- [ ] 测试集达到 300 到 500 条，类别分布符合约定。
- [ ] 每条样本有期望行为、相关块/页码、版本与来源标注。
- [ ] 评估可复现 Recall@k、MRR、nDCG、忠实度、答案相关性。
- [ ] 基线与阶段二结果可对比，报告包含逐题明细与差异。
- [ ] 硬门槛通过：越权召回 0、废止召回 0、旧版本引用 0。
- [ ] 软门槛达到约定值，未达标项有原因与处理计划。
- [ ] 评估任务失败不影响问答主流程。

### 14.6 人工转接

- [ ] 无引用/拒答时用户可发起转人工，生成唯一转办号。
- [ ] 转办单自动分配到知识库归属部门，状态为待受理。
- [ ] 部门管理员可受理、回复、办结、退回；退回必须填写原因。
- [ ] 用户可在「我的反馈」查看状态与回复，不能查看他人转办。
- [ ] 转办快照由后端按消息 ID 生成，客户端篡改无效。
- [ ] 转办操作有审计记录。

## 十八、待确认事项

1. **部门范围**：首期只接入教务处，需确认教务处责任人与文档清单。
2. **角色映射**：`user` 迁移为 `student` 是否影响现有账号；是否需要保留 `user` 兼容别名。
3. **文档可见性级别**：是否只使用 public / department / admin_only 三级；是否需要更细的文档级白名单。
4. **敏感文档范围**：哪些文档属于 `admin_only`；本阶段是否完全不进入问答。
5. **版本号规则**：按年份、修订次数还是部门自定义；旧版本保留多久。
6. **生效日期**：发布即生效，还是必须指定生效日期；未来生效版本是否允许提前发布。
7. **测试集来源**：教务处能提供多少真实工单；脱敏与审核由谁负责。
8. **评估门槛**：Recall@5、引用正确率、忠实度、拒答正确率的最终阈值。
9. **性能目标**：目标硬件是否含 GPU；P95 目标值；是否接受批量化精排。
10. **人工转接时限**：首次响应与办结时限；超时如何处理。
11. **旧数据迁移**：阶段一数据是否需要迁移到新角色/部门模型；迁移窗口与回滚方案。
12. **部署位置**：校内机房、云主机还是学校算力平台；备份介质与保留周期。

## 十九、与总方案、阶段一和阶段三的关系

- 本文件落实《项目落地方案.md》第二阶段「能信」的核心内容，并补齐阶段一延后的 P0/P1 治理项。
- 阶段一解决「谁能进、进哪个端、能做什么、如何反馈」；阶段二解决「答案依据是否有效、是否有权、是否可核验」。
- 阶段二完成后，系统具备「文档有权限、版本可追溯、引用可核验、质量可回归、问题可转办」的能力，为阶段三的多部门、移动端、缓存与深度问答提供数据与治理基础。
- 阶段三不得绕过阶段二的 ACL、版本与评估门槛；深度问答、缓存、移动端都必须继承本阶段的检索范围与引用规则。
