# 评分与模型选型报告

> 项目：基于混合检索与 Rerank 的校园领域知识库系统
> 日期：2026-11-24
> 范围：100 题问答测试的评分结果、分数可信度、模型能力对比与部署选型建议

---

## 一、结论摘要

| 项目 | 结果 |
| --- | --- |
| 本地 `qwen3:8b`（系统修复 + 去重后） | 82.5% |
| API `deepseek-chat`（同一套索引与题库） | **96.5%** |
| 系统侧修复带来的累计增益 | 73.0% → 82.5%（+9.5 分） |
| 换强模型带来的增益 | 82.5% → 96.5%（+14.0 分） |
| 当前剩余失分 | 6 处：数据缺陷 1、检索缺失 4、裁判偏严 1 |
| 可继续优化空间 | 约 2.5 分，方向为多跳拆分子查询，与换模型无关 |
| 部署推荐 | 24GB 单卡跑 Qwen3-30B-A3B（AWQ），预计 93–95%；追求极限用 48GB+ 跑 Qwen2.5-72B |
| 配置修正 | Ollama `num_ctx` 由默认 4096 提升至 8192（已修复，见 6.5）；上述分数均产生于 4096，应视为下界 |

一句话：**系统修复决定上限，模型决定能不能摸到上限。** 两者是叠加关系，不是替代关系。

## 二、评分方法

### 2.1 题库

- 规模：100 题，两个知识库各 50 题。
- 配比：口语泛化 50 题、多跳推理 25 题、规范表述 25 题。
- 字段：`question`、`reference_answer`、`evidence`（引用原文与页码）、`kb_id`、`category`。
- 文件：`qa_kb3.jsonl`（KB3 学生管理规定）、`qa_kb4.jsonl`（KB4 绩效工资与成果奖励）。

### 2.2 执行条件

| 项 | 设置 |
| --- | --- |
| 账号 | admin（可检索全部文档，含 `admin_only`） |
| 检索策略 | id=1，混合检索 + 精排（向量 + BM25 → RRF → 精排 top5） |
| 知识库 | KB3 =「学生管理规定」类；KB4 =「绩效工资与成果奖励」类 |
| 模型 | 本地 `qwen3:8b` / API `deepseek-chat` |
| 生成模式 | fast（非 Agent） |
| 上下文长度 | 测试时为 Ollama 默认 4096（后已修复为 8192，详见 6.5） |

### 2.3 判分口径

采用三档制，与参考答案逐条比对：

| 档位 | 判定标准 |
| --- | --- |
| 1.0 正确 | 核心结论、关键数值、依据条款均正确；允许表述更详细或补充相关条款 |
| 0.5 部分正确 | 核心结论正确，但遗漏关键数值/条款，或补充了与题意相关但非必需的内容 |
| 0.0 错误 | 拒答（称“未找到依据”）、结论与参考答案冲突、关键数值错误 |

说明：

- 拒答一律记 0.0，不因“语气谨慎”给分。
- 关键数值错误按 0.0 处理，例如把 360 分算成 320 分。
- 表述冗余、格式差异不扣分。

### 2.4 裁判

- 本轮 100 题由评测助手逐题人工判分，非 API 自动裁判。
- 局限：判分者与答题模型同源，存在自评偏高风险，详见第五节。

| 规范表述 | 72.0% | 90.0% | 90.0% | 100.0% |

### 3.2 API 轮判定分布

| 判定 | 题数 | 占比 |
| --- | --- | --- |
| 正确（1.0） | 94 | 94% |
| 部分正确（0.5） | 5 | 5% |

### 3.3 耗时

| 模型 | 平均单题耗时 | 说明 |
| --- | --- | --- |
| `qwen3:8b`（本地） | 25.6 秒 | 生成占主要部分 |

## 四、剩余失分分析

API 轮仅 6 处失分，逐条如下。

| 题号 | 得分 | 模型实际回答 | 原因 | 归类 |
| --- | --- | --- | --- | --- |
| kb4-oral-016 | 0.0 | 逐个排除了省级教学案例 100、教材奖 5000、教学团队 1000，明确判定“不是教学成果奖”，最终拒答 | 表 3 合并单元格丢失“教学成果奖”项目名 | 数据缺陷 |
| kb4-hop-001 | 0.5 | 答了“就高不重复”，未给 200 万奖励和 15000 分 | 专项奖励金额表未进 top5 | 检索缺失 |
| kb4-hop-002 | 0.5 | 奖励 15.6 万算对，但称“未见专利转化计分条款” | 第九条 10 分/万元未进 top5 | 检索缺失 |
| kb4-hop-007 | 0.5 | 50%/50% 规则答对，称“未给出重点项目具体分值” | 表 1 的 400 分未进 top5 | 检索缺失 |
| kb4-hop-009 | 0.5 | 只答 50% 折算，且引用的是人文社科第七条 | 一级期刊 2000 分表未进 top5，且跨附件串台 | 检索缺失 |
| kb3-oral-011 | 0.5 | 三好学生 10%、百优班级加名额均答对，未答优秀学生干部 | 题干只问三好学生，参考答案含学干部分 | 裁判偏严 |

结论：

1. **数据缺陷 1 处**：`oral-016`，合并单元格导致项目名缺失，解析代码已修复，需重跑索引生效。
2. **检索缺失 4 处**：`hop-001/002/007/009` 的模型回答都明确写着“参考资料未给出分值”，并未编造。这 4 题的共同点是同一个问题需要“规则块 + 分值表块”两类证据，单次检索的 top5 往往只覆盖其中一类，属于**多跳检索**问题，不是模型推理问题。
3. **裁判偏严 1 处**：`kb3-oral-011` 的题干只问三好学生，参考答案却包含优秀学生干部名额，建议修题干或放宽判定。
4. 另有 1 处题库口径问题：`kb4-hop-008` 题干只说“省级 B1 类第一等级”，而表 4 中“国创赛省赛 400 / 挑战杯省赛 300”均成立，参考答案取 300，建议题干补明赛事名称。

### 4.1 可修空间与对应措施

| 措施 | 可解题 | 预期收益 |
| --- | --- | --- |
| 多跳拆分子查询（先查规则，再按规则提到的对象查分值表） | hop-001 / 002 / 007 | +1.5 |
| 多跳时扩大精排名额（top5 → 8–10） | 同上，可部分缓解 | +1.0 左右 |
| 加强跨附件族过滤 | hop-009 | +0.5 |
| 合并单元格修复（代码已改，待重跑索引） | oral-016 | +1.0 |
| 题干或判定口径复议 | kb3-oral-011 | +0.5（非系统问题） |

即当前 96.5% 中仍有约 **2.5 分属系统侧可修**，主要方向是多跳检索而非更换模型。

### 4.2 对“部分正确”的说明

部分正确（0.5 分）在这轮 API 测试中全部表现为“规则答对、数值缺失”。这一特征说明模型并非不懂制度，而是上下文里没有出现对应数值表；同时也说明三档判分对“数值完整性”的要求高于“规则正确性”。

### 4.3 本地模型（qwen3:8b）失分结构

本地模型在去重后一轮共 26 处失分：9 题 0 分、17 题 0.5 分，合计丢 17.5 分。

**9 道 0 分**

| 类型 | 题号 | 模型表现 |
| --- | --- | --- |
| 拒答 | oral-010、oral-016、formal-012 | “未找到依据”“资料未明确” |
| 结论相反 | hop-002、formal-011 | “转化金额与计分无关”“第七条未提及” |
| 数值用错 | hop-008、hop-010 | 600 分算成 3000（应为 300×5）；400×80%=320（应为 360） |
| 关键数值全缺 | hop-001 | 只答“就高不重复”，200 万与 15000 分均未给出 |
| 自相矛盾 | kb3-oral-007 | 先说迟到不算旷课，后文又列“迟到 2 次算 1 学时” |

**17 道 0.5 分**

| 类型 | 数量 | 题号 |
| --- | --- | --- |
| 缺关键数值 | 7 | hop-003、hop-005、hop-007、hop-009、formal-007、oral-016（KB3）、oral-024 |
| 缺关键条件 | 5 | oral-005、oral-012、oral-022、hop-006、oral-024（KB4） |
| 编造无依据细节 | 3 | oral-024（KB3，“6 个月补申”）、hop-005（“延长 15 日”）、hop-011（“2/3 成员同意”） |
| 引用或名称错误 | 2 | oral-004（文件名错）、hop-007（KB3，引成五十七条） |

**按知识库分布**

| 知识库 | 失分 | 特征 |
| --- | --- | --- |
| KB3 | 6.0 分（11 题） | 10 题为“找得到、答不全”或“添油加醋”，仅 1 题拒答 |
| KB4 | 11.5 分（15 题） | 8 题 0 分，拒答与数值错误各占一半 |

**与 API 轮的失分类型对照**

| 失分类型 | qwen3:8b | deepseek-chat |
| --- | --- | --- |
| 拒答或判未找到 | 4 | 1 |
| 数值错误或缺失 | 8 | 4 |
| 缺关键条件 | 5 | 1 |
| 编造无依据细节 | 3 | 0 |
| 引用错误 | 2 | 0 |
| 自相矛盾 | 1 | 0 |

**结论**

1. 8B 的主要问题不是“找不到条款”：KB3 的 10 道半对题都命中了正确条款，失分在答不全或自行加内容，属指令遵循与自检能力不足。
2. 编造细节是 8B 独有的问题：3 道半对题出现原文没有的“6 个月补申”“延长 15 日”“2/3 成员同意”，API 轮为 0。这类错误在高危场景比拒答更危险。
3. 数值缺失是两代模型共有的问题：8B 8 处、API 4 处，根因都是分值表未进 top5，属检索侧的多跳问题，与模型能力无关。

## 五、分数可信度

### 5.1 已知偏差来源

| 来源 | 影响 | 处置建议 |
| --- | --- | --- |
| 裁判与答题模型同源 | 可能高估 2–4 分 | 人工抽检 20 题，覆盖 KB4 多跳与规范表述 |
| 单次生成波动 | ±3–5 分 | 关键题重复 3 次取均值 |
| 题库口径歧义 | 个别题无法判定唯一正确答案 | 修订题干（如 hop-008） |
| 8B 与 API 判分宽严不一致 | 轻微 | 两轮均已用同一三档口径复评 |

### 5.2 建议的复核方式

1. 抽检 20 题（KB4 多跳 8 题 + KB4 规范 6 题 + KB3 随机 6 题），人工逐条核对。
2. 对抽检结果计算“裁判一致率”，若低于 90%，对全部 100 题重判。
3. 正式对外发布前，报告中的准确率注明“AI 辅助判分，人工抽检 X 题一致率 Y%”。

## 六、模型选型

### 6.1 本地开发机（RTX 4060 Laptop，8GB 显存 / 16GB 内存）

本地仅用于开发验证，不是部署目标。可达上限约 88–91%。

| 方案 | 显存 | 预计得分 | 单题耗时 | 说明 |
| --- | --- | --- | --- | --- |
| `qwen3:8b`（现用） | ~5GB | 82.5% | 26 秒 | 基线 |
| `qwen3:8b` 开思考模式 | ~5GB | 约 86–89% | 60–90 秒 | 零成本可测，多跳与算术收益最直接 |
| `deepseek-r1:8b`（蒸馏 Q4） | ~5GB | 约 86–89% | 80–150 秒 | 推理链强，输出啰嗦 |
| `glm4:9b` Q4 | ~6GB | 约 85–88% | 30–40 秒 | 中文表达稳，算术一般 |
| `qwen2.5:14b` Q4 | ~9GB | 约 88–90% | 90–180 秒 | 需部分卸载到内存 |

预计分数按本轮失分结构外推，非实测。

### 6.2 服务器选型

| 显存档位 | 推荐模型 | 量化 | 预计得分 | 说明 |
| --- | --- | --- | --- | --- |
| 24GB（4090 / L4 / A10） | **Qwen3-30B-A3B-Instruct** | AWQ int4 | 约 93–95% | MoE 仅激活 3B，速度约为同规模稠密的 3 倍，**首选** |
| 24GB | Qwen3-32B | AWQ int4 | 约 94–96% | 稠密模型更稳，吞吐略低 |
| 48GB（L40S / A6000 / 2×24G） | Qwen3-30B-A3B | bf16 | 约 94–95% | 双卡 bf16，量化损失最小 |
| 48GB | Qwen2.5-72B-Instruct | AWQ int4 | 约 95–96% | 条文理解最强档开源模型 |
| 80GB（A100 / H100） | Qwen3-32B | FP8 | 约 95–96% | 并发高、延迟低，适合多用户 |
| — | DeepSeek-V3 API | — | 96.5% | 当前基线，作为兜底 |

### 6.3 推荐理由

1. **Qwen3-30B-A3B 是本场景性价比最优解**：30B 总参数、3B 激活，单张 24GB 卡即可运行，中文制度文本与多跳推理显著强于 8B，吞吐更适合校园并发场景。
2. **追求稳定性选 Qwen3-32B**：稠密结构在长条文和数值计算上更可预期，代价是吞吐下降。
3. **48GB 以上选 Qwen2.5-72B**：中文条款理解最强，是本轮 API 结果最接近的开源替代。
4. **8GB 显存无路径达到 96.5%**：这不是调参问题，参数规模决定的能力上限。

### 6.4 部署栈建议

| 组件 | 建议 | 理由 |
| --- | --- | --- |
| 推理引擎 | vLLM | 支持 AWQ / FP8、前缀缓存，RAG 首 token 延迟可压到 1 秒内 |
| 嵌入模型 | bge-m3（GPU） | 当前在 CPU 上，是检索耗时的主因 |
| 精排模型 | bge-reranker-v2-m3（GPU） | 同上，CPU 精排单题可达数秒 |
| 上下文长度 | 8K 足够 | 每次仅喂 5 个块，无需 128K |
| 量化 | AWQ int4 起步，显存宽裕再上 FP8 | 精度损失小、显存友好 |

### 6.5 上下文长度配置（已修复）

模型选型之外，上下文长度是一个容易被忽略、但会直接吞掉证据的配置项。

**问题**

| 项 | 数值 |
| --- | --- |
| Ollama 默认 `num_ctx`（未显式设置时） | 4096 |
| 单次请求上下文用量 | `CONTEXT_MAX_CHARS=3500` 正文（约 2500–3500 token）+ 系统提示约 500 token + `LLM_MAX_TOKENS=2048` 输出预算 ≈ **5500–6000 token** |
| 结果 | 超出后被静默截断，被丢弃的通常是最前面的高排名块 |

这与测试中观察到的现象一致：证据在 top5 却回答“未找到”（oral-010、oral-016、formal-012）、自相矛盾（kb3-oral-007）、关键数值缺失（hop 系列）。模型并非没有能力，而是输入被截短。

**修复**

- 在启动 Ollama 前设置 `OLLAMA_CONTEXT_LENGTH=8192`，并写入用户环境变量以固化。
- 实测 `ollama ps`：`qwen3:8b` 上下文 8192、100% GPU、占用 6.2GB。
- 机器上已有的 `qwen3-8b-16k`（`num_ctx 16384`）实测为 20% CPU / 80% GPU、7.8GB，KV 缓存挤占显存会导致明显变慢，**8GB 卡上 8192 是最佳点**，不建议使用 16k 变体。
- 项目 `.env` 中已补充该变量与说明注释，避免换机后再次踩坑。

**对测试结论的影响**

此前 100 题结果均在 4096 上下文下产生，理论上存在低估；本报告未重跑，因此 96.5%（API）与 82.5%（本地）应视为**下界**。重新测试时应在 8192 起步的配置下进行。

**服务器部署对应项**

- vLLM 需同步设置 `--max-model-len 8192` 起步；若后续接入多轮对话或更大 top_n，再提升到 16384。
- 上下文变长会增加 KV 缓存占用，选型时需把显存预算一并计算，而不是只看模型权重。

### 6.6 混合路由建议

最实用的折中方案：

- 常规问题（单条款、单文件、字数少）→ 本地 30B 模型。
- 命中“多跳 / 计算 / 跨文件 / 多表对比”特征 → API 兜底。
- 预期整体落在 **95% 以上**，同时把 API 成本压到只覆盖复杂问题。

## 七、落地验收标准

### 7.1 口径说明

96.5% 是严格三档口径（拒答记 0、数值错记 0）。若按"完全正确"计算为 94%，按"答对或部分对"计算为 96.5%。**验收应看完全正确率，不看含部分分的总分。**

### 7.2 分阶段验收线

| 阶段 | 总体（完全正确） | 高危题 | 严重错误率 | 附加条件 |
| --- | --- | --- | --- | --- |
| 内测试点 | ≥ 85% | ≥ 90% | 0 | 必须带引用，可一键转人工 |
| 部门推广 | ≥ 90% | ≥ 95% | 0 | 用户可反馈纠错，有人值守 |
| 全校开放 | ≥ 95% | ≥ 98% | 0 | 灰度发布 + 每周抽检 |

高危题指涉及**金额、比例、期限、处分、资格认定**的问题。这类题答错的危害远大于答不出。

### 7.3 三条红线

1. **严重错误率必须为 0**：给出错误金额、错误期限、错误处分档次，一次即可造成投诉；宁可拒答。
2. **高危题必须带原文引用**：现有 citation 机制应保留为硬约束，不能因追求回答流畅而放开。
3. **拒答率保持在 5%–15%**：零拒答通常意味着模型在猜；但也不能压到"无依据仍硬答"。

### 7.4 当前定位

| 指标 | 当前值 | 判断 |
| --- | --- | --- |
| 总体（严格三档） | 96.5% | 超过"全校开放"线 |
| 完全正确率 | 94% | 介于"部门推广"与"全校开放"之间 |
| KB4 绩效与奖励 | 94% | 短板，刚卡在推广线 |
| 多跳推理 | 92% | 短板，低于推广线 3 分 |
| 严重错误 | 1 处（oral-016 为拒答，非错答） | 符合红线 |

结论：**可进入小范围试点，尚不宜直接全校开放。** 两个卡点：

1. 多跳 92% 低于推广线的 95%，失分集中在"缺最终数值"，建议试点期间将多跳类问题路由到 API 模型。
2. 样本仅 100 题，96.5% 的 95% 置信区间约为 91%–99%，波动约 5 个百分点；定稿至少需 300 题，或同题复跑 3 次取均值。

### 7.5 上线后应监控的业务指标

| 指标 | 说明 | 建议频率 |
| --- | --- | --- |
| 引用命中率 | citation 是否真正支撑结论 | 人工抽检 20 题/周 |
| 转人工率 | 偏高说明覆盖不足；过低需警惕用户盲信 | 每周 |
| 重复提问率 | 同一问题反复提问，通常说明首次答案不可用 | 每周 |
| 高危题错答数 | 出现 1 次即回滚该批索引 | 按周统计 |

一句话：**总分 90% 是门槛，高危题 95% + 零严重错误才是准入条件，样本量决定这个分数能不能信。**
